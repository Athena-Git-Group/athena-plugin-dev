# Rule 1 - 逐 phase 檢查 artifact 與 gate，已完成的 phase 跳過不重跑

- Level: `MUST`
- 開工前逐 phase 檢查 artifact 是否已存在且非空、gate 是否已過：score 看 `score/score-report.md` 首行 VERDICT、clarify 看 `clarify/clarified.md` 首行 STATUS、**specify 看 `specify/spec.md` 首行 `STATUS: READY`**。
- 已完成的 phase **跳過不重跑**，直接沿用既有 artifact 往下走。
- 這道檢查讓 clarify FAIL → 使用者補答 → flow 重跑 spec stage 的迴圈成本最小化。

## Good Example

- 這個例子是好的，因為它逐 phase 看 artifact 與 gate 狀態，只重跑真正還沒完成的部分。

````md
score/score-report.md 首行 VERDICT: PASS-CLEAN → 跳過 score
clarify/clarified.md 首行 STATUS: RESOLVED → 跳過 clarify
specify/spec.md 不存在 → 從 specify 開始跑
````

## Bad Example

- 這個例子是壞的，因為它每次重跑都把所有 phase 從頭跑一遍，使用者補答一題就要付整輪的成本。

````md
spec stage 重跑 → 不看既有 artifact，直接從 score 重跑到 gherkin
````

# Rule 2 - gate 未過不算「已完成」，一律重跑且不得沿用該 artifact

- Level: `MUST`
- **gate 未過不算「已完成」**：`clarified.md` 首行為 `STATUS: BLOCKED`、或 `spec.md` 首行為 `STATUS: NEEDS-CLARIFICATION` 時，該 phase **一律重跑**，**不得**當成已完成跳過、**不得**沿用該 artifact 往下走。
- 重跑前先納入可能已更新的 `clarify/answers.md`，讓這一輪帶著使用者的新回答執行。

## Good Example

- 這個例子是好的，因為它辨識出 artifact 雖然存在但 gate 未過，於是帶著新的 answers.md 重跑該 phase。

````md
clarify/clarified.md 存在，首行 STATUS: BLOCKED
→ 先讀 clarify/answers.md，再重跑 clarify
````

## Bad Example

- 這個例子是壞的，因為它只看「檔案存在且非空」就判定已完成，讓 BLOCKED 的產出被下游當成已澄清的需求。

````md
clarify/clarified.md 存在且非空 → 跳過 clarify，直接跑 specify
````

# Rule 3 - `ui_prototype` 的續跑判定依 target 分流，backend 視為不適用

- Level: `MUST`
- 選用 phase `ui_prototype` 的判定另有規則：**`target` = `backend` 時視為不適用（等同「已完成（略過）」）**，不因缺檔重跑、不因缺檔 FAIL——backend track 本來就不執行它。
- `target` = `frontend` / `fullstack` 時看 `ui_prototype/ui-plan.md` 非空、且該目錄下至少一個 `.html` 非空，兩者皆滿足才算已完成。

## Good Example

- 這個例子是好的，因為它先看 target 再判定，backend 不會被缺檔誤判成失敗。

````md
target = backend，ui_prototype/ 不存在 → 視為不適用，不重跑、不 FAIL
target = fullstack，ui-plan.md 非空且 refund-list.html 非空 → 跳過 ui_prototype
````

## Bad Example

- 這個例子是壞的，因為它不分 target 一律要求 `ui_prototype` 的產出，backend track 會被永遠判 FAIL。

````md
ui_prototype/ 不存在 → FAIL — ui_prototype 產出缺失 #skill-defect
````
