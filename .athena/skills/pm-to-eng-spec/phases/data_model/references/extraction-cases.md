# 萃取決策樹 · 邊界案例集

> 配合 `SKILL.md` 的「萃取決策樹（名詞 → 什麼）」。本檔收錄**難判的邊界情境**，需要時參考；
> 不重述決策樹本體。每個案例格式：情境 → 判定 → 理由。

## A. enum vs reference table

- **封閉小集合、無自身屬性、不被在地化**（如付款狀態 `PENDING / PAID / REFUNDED`）→ **enum**。
- **需要被在地化 / 自帶屬性 / 被外鍵引用 / 會由營運後台增刪**（如商品分類、角色）→ **reference table**。
- 判準一句話：「這個分類值未來會不會長出自己的欄位、或需要被 join？」會 → reference table。

## B. 衍生值偽裝成欄位（stored vs derived）

- 訂單總額、年齡、帳戶餘額、「是否逾期」→ 預設 **derived**，記計算來源，不落欄。
- **例外（落欄並標 `denormalized`）**：需要歷史快照（成交當下的金額，事後不可隨單價變動）、
  或讀取效能要求高且來源資料量大。落欄時必須註明一致性維護方式（觸發點 / 重算時機）。

## C. 1:1 何時合併、何時拆

- 預設**合併進主實體**（如 user 的少數 profile 欄位）。
- **拆出獨立實體**只在：可選屬性一大群（多半為 NULL）、不同生命週期（profile 後補）、
  不同存取頻率 / 權限（敏感資料隔離）、或不同保存政策。

## D. 值物件（address / money / 經緯度）

- 無獨立身分、只依附主實體 → **嵌入主實體的欄位**（`shipping_city`, `amount` + `currency`）。
- 需被多實體共享、或需獨立查詢 / 維護（如標準地址簿）→ 升格 **獨立實體**。
- money 一律「金額 + 幣別」兩欄，勿只存數字。

## E. 同義詞合併 / 一詞多義拆分

- 會員 / 用戶 / 客戶在需求裡指同一真實事物 → **合併為一個 entity**，別名記在來源欄。
- 同一個「訂單」在「下單」與「出貨」情境語意不同（前者購物車結果、後者物流單位）→
  **拆成不同 entity**（Order / Shipment），各自命名。

## F. N:M 帶屬性 → associative entity

- 選課（帶成績、選課時間）、訂單明細（帶數量、單價）、標籤關聯 → 一律 **associative entity（junction）**，
  關係上的屬性掛在 junction，不要硬塞進任一端。

## G. 階層 / 樹狀資料（分類目錄、組織架構）

- 淺層、查詢單純 → **self-referencing FK**（`parent_id`）。
- 需頻繁查整條祖先 / 子孫鏈 → 線索：closure table / path enumeration（屬物理層，這裡先標「階層 + 查詢需求」交給 db_table）。

## H. 多型 / 變體（付款方式、通知管道）

- **概念層只標為「一個 entity + 一個 type 欄位（封閉值集合）」**，例如 `Payment(type, ...)`。
- **不要在 data_model 做 OOP 介面抽象**——那是 class_diagram（物件設計）的事。
  本層只負責「有這個變化點、值集合是什麼」，物件怎麼抽介面留給下游。

## I. 歷史 / 時間維度需求

- 「要看某時間點的狀態 / 變更軌跡」→ 線索：history 表（每次變更一列）、快照表（定期全量）、事件表（append-only）。
- 本層先標「該實體需保留歷史 + 哪種讀取需求」，落地形式可在 handoff 留建議。

## 命名慣例（預設建議，團隊可覆寫）

> 以下為通用慣例，非團隊定論；團隊有既有規範時以團隊為準。

- 實體名用**單數名詞**、概念層用可讀的中/英文皆可（落地命名交給 db_table）。
- junction 用兩端實體組合命名（如 `Enrollment` 表選課，或 `Student_Course`）。
- enum 值用大寫 `SNAKE_CASE`、語意明確、避免縮寫。
