# `spec.md` 的節結構與填寫判準

> 本檔是 `specify` phase 產出 `specs/<slug>/specify/spec.md` 的結構契約。
> `spec.md` 是**結構層與其後所有 phase 的唯一需求真源**——下游
> （`data_model` / `class_diagram` / `db_table` / `screens` / `api` / `ui_contract` / `gherkin`）
> 只讀它，不再回讀 `clarify/clarified.md`。因此**這份結構少一節，下游就少一種素材**。

## 0. 首行 STATUS（機械契約）

第一行必為下列其一，編排器只認這一行：

```
STATUS: READY
STATUS: NEEDS-CLARIFICATION
```

`READY` 代表本檔可作為下游的唯一需求真源；`NEEDS-CLARIFICATION` 代表仍有高影響缺口
已追寫到 `specs/<slug>/clarify/questions.md`，編排器會停止並回報使用者。

## 1. 必含節總表（缺任一節即未完成）

|---|----|------|---------|---------------|
| 1 | 使用者故事 | 依商業價值排序、標 Priority、每個可獨立驗證、含驗收情境與**故事專屬 FR / NFR** | `clarified.md` 的業務目標 / 角色 / 行為 | `screens`、`gherkin` |
| 2 | 邊界情況 | 每條帶**具體觸發值** | `clarified.md`「邊界」段 | `gherkin`（邊界優先） |
| 3 | 全域需求 | 只放無法歸戶單一故事的 FR / NFR | `clarified.md` 規則段 | `api`、`class_diagram` |
| 4 | 關鍵實體 | 實體名 + 業務語意（一句） | `clarified.md` | `data_model` |

## 2. 節 1 · 使用者故事

每個故事的最小完整形態（缺任一項視為故事未完成，而非格式已合格）：

```md
### 使用者故事 1 — <可獨立交付的使用者成果> (Priority: P1)

作為 <角色>，我希望 <行為>，以便 <價值>。

**為何為此優先級**: <排序理由；對齊交付依賴與商業價值，不是敘述順序>

**獨立驗證方式**: <只實作這個故事時，如何驗證它成立>

**驗收情境**:
1. **Given** <前提>，**When** <操作>，**Then** <可觀察結果>

**功能需求（FR）**:
- **FR-001**: 系統 MUST <可驗證的行為>

**非功能需求（NFR）**:
- **NFR-001**: <可量測的品質要求>
```

- 故事必須是**使用者價值切片**，不是實作步驟、資料處理細節或 UI 元件名稱。
- NFR 若確實沒有，**刪掉該小節**，不留空殼。
- 切分與排序的完整判準見 `story-splitting.md`。

## 3. 節 2 · 邊界情況（判定值的第一來源）

沿用 `clarify` 對「邊界」段的既有要求：**每條寫成帶具體觸發值的條目**，
讓 `gherkin` 能直接寫成 `例子` 列，不必回頭猜。

- ✅ 「退款金額上限 = 訂單金額；訂單 1000 時退 1001 應拒，回 `REFUND_EXCEEDS_ORDER`」
- ❌ 「退款金額不能太大」「要處理超額的情況」

上游有觸發值就**逐字搬**；上游沒有觸發值代表 clarify 未達完成判準——列為缺口，不自己編。

## 4. 節 3 · 全域需求

只保留會同時約束多個故事、或本質上無法指派給單一故事的 FR / NFR。
全域需求段是**例外處理，不是需求集散地**——把所有 FR 集中回來就破壞了歸戶結構。
同一條需求歸戶後只出現在一處，編號唯一；別處要提及只能寫敘述性說明，不重複編號條目。

## 5. 節 4 · 關鍵實體

實體名 + 一句業務語意。**這一節只負責「有哪些實體」，不負責資料細節**——
資料細節一律在節 5。只寫到這一節就交出去，等於把 `data_model` 的素材丟掉。

## 6. 節 5 · 資料維度與範例資料（**本 pack 追加，承載義務的核心**）

> 這一節是**本 pack 相對於外部 SDD 骨架的必要追加**。少了它，`data_model` 沒有值域 /
> 基數 / 身分可萃取，`gherkin` 沒有判定值可溯源，而**機械 gate 全過**——
> 典型的靜默半生效。**任何情況下都不得刪除或以摘要代替這一節。**

### 6.1 資料維度（每個核心實體一小節）

逐項承載 `clarified.md`「資料維度」段的答案，缺項標「未指定」而非略過：

| 維度 | 要寫什麼 |
|------|---------|
| 身分與唯一性 | 哪個欄位（或欄位組合）唯一辨識一筆；條件式唯一也要寫 |
| 關係與基數 | 1:1 / 1:N / N:M + 方向、存在性、刪除行為（業務語言） |
| optionality | 每個業務欄位是否必填 |
| 值域 | 資料種類（文字 / 數字 / 日期 / 金額 / 布林 / 列舉）、精度（金額小數位、時間時區）、列舉的**完整封閉集合**與預設值 |
| 狀態 | 狀態集合與合法轉移（誰能從哪個狀態到哪個狀態） |
| 保存 | 是否留歷史 / 變更軌跡；保存多久、能否硬刪、法遵要求 |
| PII | 哪些是個資 / 敏感欄位，是否需遮罩 / 加密 / 存取限制 |
| 量級 | 預期資料量級與成長（至少數量級） |
| 多租戶 | 多租戶與隔離邊界（若適用）：隔離邊界劃在哪、用什麼識別租戶。不適用時明寫「不適用」而非略過 |
| 存取樣式 | 主要查詢條件、排序 / 分頁、高頻查詢欄位 |

### 6.2 範例資料（**逐筆搬運，不摘要、不改值**）

- **每個核心實體 ≥ 3 筆真實範例資料**，用表格或條列逐筆列出全部欄位值。
- 值必須與 `clarified.md` **逐字一致**——這些值會被 `gherkin` 當判定值直接寫進
  `.feature`，也會被 `ui_contract` 當 fixtures 素材；改一個值就是改了下游的驗收。
- ❌ 「範例資料見 clarify 的紀錄」「約 3 筆訂單資料」「（略）」——這三種寫法都是承載失敗。
- 上游不足 3 筆時：列為缺口（走缺口升級協議或寫進假設），**不得自行編造補足**。

範例形狀：

```md
#### 範例資料 · Order

| id | customer_id | status | total_amount | created_at |
|----|-------------|--------|--------------|------------|
| 1001 | C-001 | PENDING | 1000.00 | 2026-01-05T09:00:00+08:00 |
| 1002 | C-002 | PAID    |  250.50 | 2026-01-06T14:20:00+08:00 |
| 1003 | C-001 | REFUNDED| 1000.00 | 2026-01-07T11:05:00+08:00 |
```

## 7. 節 6 · 成功標準（SC-nnn）

- 可量測、可驗證、**技術中立**（不寫框架 / 資料庫 / API 形式）。
- 職責邊界：成功標準是**業務層成果**，**不是**第二份驗收真源。
  `.feature` 場景一律溯源到 FR / 邊界情況 / 範例資料，不直接由 SC 生成。
- 下游 `gherkin` 的義務是「每個 SC-nnn 至少被一個 `Rule` 區塊涵蓋，或在 handoff 明列
  『本階段不涵蓋 + 理由』」——所以 SC 要寫得能被對照，不要寫成空泛願景。

## 8. 節 7 · 假設

只記錄「目前推理成立所依賴的前提、範圍邊界、既有條件」。
判準：**某條內容一旦拿掉就會改變產品必備行為 → 它是需求，不是假設**，請改寫成 FR / NFR。

## 9. 節 8 · 承載覆蓋帳本（**不得有「未處理」**）

沿用本 pack `data_model` 的「覆蓋帳本」慣例：用一張表證明上游沒有任何內容在轉換中掉落。

| clarified.md 的來源項 | 類型 | 在 spec.md 的去向 |
|----------------------|------|------------------|
| 「業務目標」段 | 標題段 | 使用者故事 1 / 2 的敘述 + SC-001 |
| 規則：退款金額上限 = 訂單金額 | 規則 | FR-004（故事 2）+ 邊界情況第 1 條 |
| 範例資料：Order ×3 | 範例資料 | 節 5.2「範例資料 · Order」（逐筆） |
| 「非目標」段 | 標題段 | 假設第 2 條（範圍邊界） |

- 左欄必須涵蓋 `clarified.md` 的**每個標題段、每條規則、每筆範例資料**。
- 去向欄寫到**具體節與編號**，不寫「已涵蓋」這種無法查證的字樣。
- 帳本中出現任何「未處理」「待補」→ **不得**把首行寫成 `STATUS: READY`。

## 10. 未定內容的標記方式

局部細節未拍板、但不阻塞整份規格時，就地標記：

```md
- **NFR-004**: 系統 MUST 在首頁載入時提供可理解的進度回饋 [NEEDS CLARIFICATION: 尚未指定呈現方式]
```

只有當缺口會改變故事切分、需求歸戶、主要流程或成功標準時，才升級走
`specs/<slug>/clarify/questions.md` 的檔案協議（見 SKILL.md「缺口升級協議」）。
