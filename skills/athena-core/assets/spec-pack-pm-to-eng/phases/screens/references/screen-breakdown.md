# 畫面 → 元件拆解準則（扁平清單）

> 配合 `SKILL.md`。本階段只做**扁平元件清單**（每個畫面上「看得到、點得到」什麼）。
> 深一層的組合樹 / props / emits / composables **不在前端結構層產出**——前端**不畫 class diagram / 元件物件圖**；元件怎麼拆與型別契約由下游 `ui_contract`（規劃綁定）與 Nuxt 4 實作承接。

## 扁平清單 vs 下游 ui_contract 的差別

| | screens（本階段） | ui_contract（下游） |
|---|---|---|
| 產出 | 每畫面一份**扁平**元件 / 可操作元素清單（業務語言） | view model + 互動→事件→(API/導航) 綁定 + API 層規劃（Nuxt 4 慣例 / typed） |
| 問題 | 畫面上**有什麼** | 資料 / API **怎麼綁上去、型別契約是什麼** |
| 形態 | 條列 | Markdown 表格（無 class diagram） |

## 怎麼列扁平清單

對每個畫面，分兩類列：

**顯示元素**（給使用者看的）：
- 標題、訂單表格、訂單明細卡、金額、狀態標籤…

**可操作元素**（使用者點 / 輸入的）——這些是下游 gherkin 互動場景的來源：
- 按鈕（「申請退款」「返回」）、輸入框（退款金額）、連結（點某筆訂單）、分頁器…

範例（訂單詳情頁）：

```
畫面：訂單詳情 /orders/:id
顯示元素：
  - 訂單編號、客戶、金額、狀態標籤、建立時間
  - 退款紀錄區塊（若已退款）
可操作元素：
  - [按鈕] 申請退款（僅客服可見、且狀態為「已付款」才 enabled）
  - [按鈕] 返回列表
```

## 元素來源：有 design/ 視覺稿就照稿列

design/ 有 Claude Design 視覺稿時，**扁平清單的元素直接從稿面盤點**（看得到什麼就列什麼），再用 `specify/spec.md` 補出現 / 啟用條件與權限。稿面沒有、但 spec.md 要求的元素，標 `待補設計` 仍列入；稿面有、需求沒提的，標 `待釐清` 回報。

## 準則

1. **可操作元素要標出現/啟用條件**（誰看得到、什麼狀態下可點）——對齊 spec.md 的 FR / 邊界情況與權限，下游 gherkin 直接拿來寫場景。
2. 元素名稱用**業務語言**（「申請退款」），不是技術元件名（`<RefundButton>`）——技術命名與型別契約是下游 ui_contract / Nuxt 4 實作的事。
3. 只列 spec.md / screen-map 導出的元素，**不自行加需求沒提的功能鍵**（非協商規則 #1）。
4. 重複出現在多畫面的元素（如全站導覽列、麵包屑）標「共用」，提示下游可抽共用元件（Nuxt `components/` auto-import）。
