# 邊界覆蓋檢查表（QA shift-left）

> 配合 `gherkin-guide.md` §5（邊界優先）與 §7（缺則回報）。
> 本檔是 gherkin 階段的「QA 探索清單」：對每條規則逐類掃一遍，把邊界 / 錯誤路徑寫成**第一級場景**，並在發現需求未定義時**回饋上游**而非腦補。

## 核心思想：把邊界探索前置

傳統流程裡，邊界值是測試最後才補的東西。本版把它**移到最前面**：

- 邊界是**最容易暴露「PM 沒講清楚」**的地方。先想邊界 → 早期逼出缺口 → 早回饋。
- 邊界資訊在上游已備好：openapi.yaml 的驗證關鍵字（由 data_model 落下，見 `../../api/references/api-conventions.md` §6）+ `specify/spec.md` 的狀態機與唯一性規則（在其「資料維度與範例資料」段）。本階段是**消費並落地**這些邊界，不是重新發明。

---

## 逐類檢查表

對每條規則涉及的每個輸入 / 狀態，逐欄問「有沒有對應場景」。狀態碼語意以 `api-conventions.md` §2 為準。

| 類別 | 邊界 / 錯誤點 | 來源 | 典型結果 |
|---|---|---|---|
| **值域上下限**（金額、數量） | min−1 / min / max / max+1 | openapi `minimum`/`maximum`/`exclusiveMinimum` | 內值成功；超界 422（業務）或 400（型別） |
| **字串長度** | 空字串 / 1 / max / max+1 | openapi `minLength`/`maxLength` | 超界 400 |
| **必填 / optionality** | 缺必填欄位 / 必填給空值 | openapi `required` | 400 |
| **enum 封閉集合** | 每個合法值各一 + 一個非法值 | openapi `enum`、spec.md 列舉 | 合法 → 對應行為；非法 → 400/422 |
| **格式 / 樣式** | 合法格式 + 壞格式（email / date / 電話 / 代碼） | openapi `format`/`pattern` | 壞格式 400 |
| **數值精度**（金額小數） | 多一位小數 / 負零 | openapi 精度註記、spec.md | 依規則 400/422 |
| **業務驗證** | 通過型別但違反規則（金額超上限、額度不足） | spec.md 的 FR / 邊界情況 | 422 |
| **狀態機非法轉移** | 從不允許的狀態觸發動作（已取消的訂單再退款） | spec.md 狀態集合與合法轉移 | 409 |
| **唯一鍵衝突** | 重複建立同一筆（含條件式唯一） | spec.md 唯一性規則 / erm.dbml UNIQUE | 409 |
| **樂觀鎖衝突** | 用過期版本更新 | erm.dbml `version`（若需求觸發） | 409 |
| **資源不存在** | 對不存在的 id 操作 | — | 404 |
| **空集合 / 零筆** | 查詢無結果 / 對空列表操作 | — | 200 空陣列（非 404） |
| **權限 / 認證** | 未認證 / 無權限 | spec.md（若在範圍內） | 401 / 403（本版可能範圍外，標 handoff） |

> 比例原則：簡單 CRUD 不必每類都寫，挑該規則**真正有約束**的維度。多實體 / 有狀態 / 跨流程的複雜規則才全套掃。

## 落地到 .feature

1. 每條規則 → 先依本表列出**該規則真正存在**的邊界 / 錯誤點。
2. 同步驟、只有值在變的多個邊界 → 收進 `場景大綱` + `例子`（見 `scenario-outline-guide.md`），邊界 / 錯誤列排前、標 `@boundary` / `@error`。
3. 步驟結構不同的錯誤路徑（如狀態機非法轉移）→ 各寫獨立 `場景`，標 `@error`，排在 happy path 之前。
4. 每個判定值在 handoff 覆蓋矩陣回指來源（`openapi.yaml#...` / `spec.md#FR-00X`）。

## 缺則回報（與上游的迴圈）· 不腦補

掃邊界時最常發生：**規則的邊界值，需求根本沒定義**。例如：
- 「退款金額上限是訂單金額嗎？還是可超額退？」spec.md 沒寫。
- 「訂單在『已出貨』狀態還能不能退款？」狀態轉移表沒涵蓋。
- enum 只列了 3 個值，但沒說「收到第 4 個值」要不要報錯。

處理（對齊 `gherkin-guide.md` §7、SKILL「絕不腦補」）：

1. **不自填**任何判定值或規則。
2. 把場景標 `@待釐清`，步驟內 `# 待釐清:<具體問題>`。
3. 在 `handoffs/gherkin.md` 開「回饋訊號（待釐清缺口）」段，用 PM 看得懂的問句列出，例如：
   > - 退款金額是否可超過訂單金額？上限為何？（來源規則未定義 → ref spec.md#FR-退款）
   > - 「已出貨」訂單可否退款？（狀態轉移表未涵蓋）
4. 交由編排器決定：補進 `specify/spec.md` 後重跑 gherkin，或回退 clarify → specify 重新釐清。

> 這條迴圈就是「邊界探索 shift-left」的真正價值：**用寫測試的動作去稽核需求完整度**，而不是先信任需求、之後在實作期才踩雷。
