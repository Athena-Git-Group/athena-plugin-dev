# ADR 格式

ADR 放在 `docs/adr/`，採用連續編號：`0001-slug.md`、`0002-slug.md`，依此類推。

惰性建立 `docs/adr/` 目錄——只有當第一份 ADR 需要時才建。

## 範本

```md
# {決策的簡短標題}

{1–3 句話：脈絡是什麼、我們決定了什麼、為什麼。}
```

就這樣。一份 ADR 可以只有一個段落。它的價值在於記錄「曾經做過某個決策」以及「為什麼」
——不在於把各個區塊填滿。

## 選用區塊

只有在真正增加價值時才加。多數 ADR 不需要這些。

- **狀態（Status）** frontmatter（`提議中 | 已採納 | 已棄用 | 已被 ADR-NNNN 取代`）
  ——當決策會被重新檢視時有用
- **考慮過的選項（Considered Options）**——只有當被否決的替代方案值得記住時才寫
- **後果（Consequences）**——只有當有不顯而易見的下游影響需要點出時才寫

## 編號

掃描 `docs/adr/`，找出現有最大的編號，加一。

## 何時該提議建立 ADR

以下三點必須**同時**成立：

1. **難以反轉**——日後改變心意的成本不容小覷
2. **缺乏脈絡會令人意外**——未來的讀者看著程式碼會納悶「他們到底為什麼要這樣做？」
3. **是真實取捨的結果**——當時確有其他可行選項，而你基於特定理由選了這個

如果一個決策很容易反轉，跳過它——反正你之後會把它改掉。如果它不令人意外，沒人會納悶為什麼。
如果當時根本沒有別的選項，那除了「我們做了顯而易見的事」之外，也沒什麼好記的。

### 哪些情況符合資格

- **架構形態。**「我們用 monorepo。」「寫入模型是 event-sourced，讀取模型投影到 Postgres。」
- **context 之間的整合模式。**「Ordering 與 Billing 透過 domain event 溝通，而非同步 HTTP。」
- **帶有鎖定效應（lock-in）的技術選擇。** 資料庫、message bus、auth provider、部署目標。
  不是每個函式庫都要記——只記那些「要換掉得花上一季」的。
- **邊界與範圍決策。**「Customer 資料由 Customer context 擁有；其他 context 只能用 ID 參照。」
  明確的「不做什麼」和「做什麼」一樣有價值。
- **刻意偏離顯而易見的路徑。**「我們用手寫 SQL 而非 ORM，因為 X。」任何「合理的讀者會預期相反
  做法」的地方。這能阻止下一位工程師去「修正」一件其實是刻意為之的事。
- **程式碼裡看不見的約束。**「因為合規要求，我們不能用 AWS。」「因為合作夥伴的 API 合約，
  回應時間必須低於 200ms。」
- **被否決的替代方案，當否決理由不顯而易見時。** 如果你考慮過 GraphQL、基於微妙的理由選了 REST，
  記下來——否則半年後又會有人提議 GraphQL。
