# 可譯性評分 rubric — 共用核心（Translatability Scoring · Core）

## 維度依 target 拆檔

評分維度分前後端，由 score 階段依 target 載入對應檔：

- 後端（餵 db_table / api / gherkin）→ `rubric-backend.md`
- 前端（餵 screens / ui_contract / gherkin）→ `rubric-frontend.md`
- fullstack → 兩份都載入，各自評分、各自產缺口清單

本檔只放**兩邊共用**的：設計原則、計分尺度、裁決規則。

## 設計原則：維度因建構而封閉

維度 = 下游產物輸入需求的**聯集**。一份需求「可不可以被轉換」，等價於
「它有沒有足夠原料餵給對應的下游產物」。**唯一該新增維度的時機，是下游多了一種新產物**
——否則不要加維度、不要調權重。這就是它不需要「補充來補充去」的原因。

## 計分尺度

每維度 0–3 分：**0 缺 / 1 微 / 2 部分 / 3 充分**。
評分時**必須引用原文證據**（找得到就引那一句，找不到就標「未找到」），讓分數客觀、可複現。

## 裁決規則（規則式，無加權總分）

```text
任一「必備」維度 = 0          → VERDICT: BLOCKED
全部維度 = 3                 → VERDICT: PASS-CLEAN
其餘（無必備=0，但有 <3）    → VERDICT: PASS-WITH-GAPS
```

- **BLOCKED** — 文件撐不起對應產物。停流程、退回 PM，附「哪個維度缺什麼」清單。
- **PASS-WITH-GAPS** — 可開工；所有 `<3` 的維度即缺口清單，**直接成為 clarify 的提問議程**。
- **PASS-CLEAN** — 原料齊備，clarify 只需最後確認。

> 哪些維度是「必備」由各 target 的 rubric 檔標記（表格 `必備` 欄）。
> **fullstack**：任一 target 出現必備=0 → 整體 BLOCKED。

## 為什麼不用加權總分

加權總分要永遠調權重，且分數不可複現（同份文件兩次評不一樣）。改用「逐維度 0–3 + 規則式裁決」：
沒有權重可調、維度封閉、每分都有原文證據——所以**不需要補充來補充去**。
