# `requirements-checklist.md` 的產生判準

> `specify` phase 的第二份產出：`specs/<slug>/specify/requirements-checklist.md`。
> 它是 `spec.md` 的**規格品質自檢**——全項勾選、或明確標「不適用 + 理由」，
> 才可把 `spec.md` 首行寫成 `STATUS: READY`。

## 使用方式（寫進 checklist 檔頭）

- 依**目前** `spec.md` 的內容逐項檢查，不是依記憶或依打算要寫的內容。
- 未通過的項目：不勾，並在「問題與修正紀錄」寫具體落差與修正方向，然後回頭修 `spec.md`。
- 仍保留的 `[NEEDS CLARIFICATION: …]`：明確說明它**是否阻塞**下游結構層。
- 不適用的項目：標 `不適用 — <理由>`，不得直接勾選帶過。

- [ ] 邊界情況的觸發值與上游一致
- [ ] 「承載覆蓋帳本」涵蓋 `clarified.md` 每個標題段 / 每條規則 / 每筆範例資料
- [ ] 承載覆蓋帳本**沒有任何「未處理」「待補」**

- [ ] 只有會改變故事切分 / 需求歸戶 / 主要流程 / 成功標準的高影響缺口才升級
- [ ] 本輪升級題數 ≤ 3，且是**追寫**到既有的 `specs/<slug>/clarify/questions.md`
- [ ] 低風險未定細節已用 `[NEEDS CLARIFICATION: …]` 或「假設」段揭露
- [ ] 仍保留的 `[NEEDS CLARIFICATION: …]` 已標示是否阻塞下游結構層

- [ ] 驗收情境足以驗證主要成功路徑
- [ ] 成功標準可量測、可驗證且技術中立，編號 `SC-nnn`

## 判準

1. **checklist 是自檢紀錄，不是儀式**——每一項都要真的回頭對照 `spec.md` 才勾。
   「看起來應該有」不算通過。
2. **「承載完整性」那一組不得跳過**。它對應的是本 pack 相對外部 SDD 骨架的追加段；
   跳過它 = `spec.md` 只剩敘述層，而下游 `data_model` / `gherkin` 會在真的跑的時候
   才失去素材，屆時沒有任何 gate 會報錯。
3. **有未勾的項目就不能寫 `STATUS: READY`**——除非該項標了「不適用 + 理由」。
4. checklist 與 `spec.md` **同批更新**：修了 `spec.md` 就回頭重跑 checklist，
   不留下與現況不符的舊勾選。
