# Rule 1 - 【51 守衛子句】先處理例外情況並提早返回

- Level: `SHOULD`
- 目的：先處理例外情況並提早返回。
- 指令句：「用守衛子句改寫巢狀 if，先用 return 處理例外情況。」
- 適用時機：巢狀 if 把主流程包在最內層，常見樣貌是 `if A { if B { if C { 主流程 } } }`。
- 操作步驟：
  1. 找出每一層 if 所守護的前提條件。
  2. 由外而內，把每個前提改成反向條件並立即 `return`／`throw`／`continue`（`if (!A) return;`）。
  3. 原本的 else 分支若是錯誤處理或預設值，搬到對應的守衛子句內。
  4. 主流程移到函式最後、零縮排層。
- 語言限制：所有主流語言皆可使用，無版本限制。
- 不適用或要小心：
  - 兩個分支都是同等重要的正常流程（不是「例外 vs 主流程」），改成守衛反而遮蔽對稱性。
  - 函式必須在單一出口做資源清理，且語言沒有 try-finally／using／defer 可用時。
- 改寫後回傳值、拋出的例外類型與副作用順序必須與原本一致。

## Good Example

- 這個例子是好的，因為例外情況全部在前面提早返回，主流程攤平在最外層。

````java
public BigDecimal discount(Order order) {
    if (order == null) return BigDecimal.ZERO;
    if (!order.isPaid()) return BigDecimal.ZERO;
    if (order.getItems().isEmpty()) return BigDecimal.ZERO;

    return order.getTotal().multiply(RATE);
}
````

## Bad Example

- 這個例子是壞的，因為三層巢狀把主流程推到最內層，閱讀時要記住所有外層條件。

````java
public BigDecimal discount(Order order) {
    if (order != null) {
        if (order.isPaid()) {
            if (!order.getItems().isEmpty()) {
                return order.getTotal().multiply(RATE);
            }
        }
    }
    return BigDecimal.ZERO;
}
````

# Rule 2 - 【52 拆解條件式】用名稱說明複雜條件

- Level: `SHOULD`
- 目的：用名稱說明複雜條件。
- 指令句：「把複雜的條件式抽成有名稱的函式。」
- 適用時機：條件式含三個以上子條件、混合 `&&`／`||`、或需要讀註解才懂其業務含義（例如 `month >= 6 && month <= 8 && isHoliday`）。
- 操作步驟：
  1. 判斷條件式表達的業務概念，取一個以 is／has／can／should 開頭的名稱（例如 `isSummerHoliday()`）。
  2. 把條件式整段抽成回傳 boolean 的函式（或區域變數，見 29 抽取變數）。
  3. 若 if／else 的分支本體也很長，一併抽成有名稱的函式。
- 語言限制：無。
- 不適用或要小心：條件本身已經一眼可懂（如 `if (list.isEmpty())`），再包一層只會多一次跳轉（此時反而考慮 31 內聯函式）。

## Good Example

- 這個例子是好的，因為條件名稱直接說出業務意圖，讀者不必解析運算式。

````typescript
const isSummerHoliday = (d: Date, holidays: Set<string>): boolean => {
  const month = d.getMonth() + 1;
  return month >= 6 && month <= 8 && holidays.has(toKey(d));
};

if (isSummerHoliday(today, holidays)) {
  applySummerRate();
}
````

## Bad Example

- 這個例子是壞的，因為讀者必須自己拼湊出「夏季假日」這個概念。

````typescript
if (today.getMonth() + 1 >= 6 && today.getMonth() + 1 <= 8 && holidays.has(toKey(today))) {
  applySummerRate();
}
````

# Rule 3 - 【53 合併條件式】集中會導向同一結果的條件

- Level: `SHOULD`
- 目的：集中會導向同一結果的條件。
- 指令句：「把結果相同的多個 if 合併為一個條件式。」
- 適用時機：連續多個 if 各自做完全相同的處理（同樣的 return 值、同樣的例外）。
- 操作步驟：
  1. 確認每個 if 的本體在語意上完全相同，且各條件沒有副作用。
  2. 用 `||`（依序判斷）或 `&&`（巢狀判斷）合併成單一條件式，保持原本的判斷順序。
  3. 合併後的條件若變得複雜，接著套用 52 拆解條件式，替它命名。
- 語言限制：無。
- 不適用或要小心：
  - 條件之間是「彼此獨立的檢查」，日後可能各自產生不同結果，合併會掩蓋差異。
  - 任一條件有副作用（呼叫會修改狀態的函式），合併後短路求值可能使某些副作用不再執行。

## Good Example

- 這個例子是好的，因為三個導向同一結果的條件被集中並命名。

````java
if (isNotEligibleForBonus(emp)) return 0;

private boolean isNotEligibleForBonus(Employee e) {
    return e.getSeniority() < 2 || e.getMonthsDisabled() > 12 || e.isPartTime();
}
````

## Bad Example

- 這個例子是壞的，因為相同的結果散成三段，日後要改回傳值時必須改三處。

````java
if (emp.getSeniority() < 2) return 0;
if (emp.getMonthsDisabled() > 12) return 0;
if (emp.isPartTime()) return 0;
````

# Rule 4 - 【54 多型】讓各型別各自實作對應行為

- Level: `SHOULD`
- 目的：讓各型別各自實作對應行為。
- 指令句：「用多型取代依型別判斷的 switch。」
- 適用時機：同一個 `switch (type)` 或 `instanceof` 鏈在多處重複出現，新增一種型別就要改多個 switch。
- 操作步驟：
  1. 為被判斷的型別建立介面或抽象父類別，宣告分支所做的行為（例如 `處理()`）。
  2. 為每個 case 建立實作類別，把該 case 的程式碼搬入。
  3. 用工廠（46 工廠函式）在單一位置把型別代碼轉成物件。
  4. 呼叫端改為直接呼叫介面方法，刪除所有重複的 switch。
- 語言限制：需支援介面／繼承或等價機制（TypeScript 可用 interface 或 discriminated union + 物件對應）。
- 不適用或要小心：
  - switch 只出現一次且分支很短，此時 60 查找表或 69 模式比對更輕量。
  - 型別集合封閉且行為種類經常增加（例如 AST 處理），此時模式比對＋窮舉檢查可能比多型更合適。

## Good Example

- 這個例子是好的，因為每個型別自帶計算行為，新增型別不必修改既有分支。

````java
interface Shape { double area(); }
record Circle(double r) implements Shape { public double area() { return Math.PI * r * r; } }
record Square(double s) implements Shape { public double area() { return s * s; } }

double total = shapes.stream().mapToDouble(Shape::area).sum();
````

## Bad Example

- 這個例子是壞的，因為同樣的 switch 會在 area、perimeter、draw 各寫一份。

````java
double area(Shape s) {
    switch (s.getType()) {
        case "circle": return Math.PI * s.getR() * s.getR();
        case "square": return s.getSide() * s.getSide();
        default: throw new IllegalArgumentException();
    }
}
````

# Rule 5 - 【55 拆分迴圈】讓每個迴圈專心做一件事

- Level: `SHOULD`
- 目的：讓每個迴圈專心做一件事。
- 指令句：「把同時做兩件事的迴圈拆成兩個。」
- 適用時機：一個迴圈同時累加多個彼此無關的結果，或同時彙整與輸出。
- 操作步驟：
  1. 複製迴圈，每份只保留一種職責。
  2. 確認兩份迴圈之間沒有依賴（第二件事不需要第一件事「同一輪」的中間值）。
  3. 拆開後把各迴圈抽成有名稱的函式，或改寫為 59 集合處理管線。
- 語言限制：無。
- 不適用或要小心：
  - 迭代來源只能走訪一次（串流、Iterator、資料庫游標），拆分會讓第二個迴圈拿不到資料。
  - 資料量極大且經量測證實多走訪一次是效能瓶頸（先量測，不可臆測）。
  - 迴圈內有外部副作用（I/O、寫入）且順序必須交錯，拆開會改變輸出順序。

## Good Example

- 這個例子是好的，因為彙整與找最年輕者各自獨立，可分別命名與測試。

````typescript
const totalSalary = people.reduce((sum, p) => sum + p.salary, 0);
const youngestAge = Math.min(...people.map(p => p.age));
````

## Bad Example

- 這個例子是壞的，因為兩件無關的計算擠在同一圈，改其中一個時容易誤動另一個。

````typescript
let totalSalary = 0;
let youngestAge = Infinity;
for (const p of people) {
  totalSalary += p.salary;
  if (p.age < youngestAge) youngestAge = p.age;
}
````

# Rule 6 - 【56 引入特殊案例】集中重複出現的特殊情況處理

- Level: `SHOULD`
- 目的：集中重複出現的特殊情況處理。
- 指令句：「把重複的空資料判斷集中到特殊案例的實作。」
- 適用時機：多個呼叫端都寫同樣的「是空的嗎？是的話用預設值」判斷（例如 `customer == null ? "occupant" : customer.getName()` 散在各處）。
- 操作步驟：
  1. 找出所有對同一特殊值（null、未知客戶、空清單）做的相同判斷與處理。
  2. 建立特殊案例物件（Null Object，例如 `UnknownCustomer`），實作與正常物件相同的介面，回傳原本各處的預設值。
  3. 在資料來源處（建立或查詢時）回傳特殊案例物件，取代 null。
  4. 逐一刪除呼叫端的重複判斷，每刪一處就跑測試。
- 語言限制：無。
- 不適用或要小心：
  - 各呼叫端對特殊值的處理並不相同，強行統一會改變行為。
  - 呼叫端需要明確知道「值不存在」以走不同流程（此時應保留 Optional／null 檢查，或用 62 快速失敗）。

## Good Example

- 這個例子是好的，因為「未知客戶」的預設行為只定義一次。

````java
class UnknownCustomer implements Customer {
    public String getName() { return "occupant"; }
    public BillingPlan getPlan() { return BillingPlan.BASIC; }
}

Customer c = site.getCustomer(); // 找不到時回傳 UnknownCustomer
String name = c.getName();
````

## Bad Example

- 這個例子是壞的，因為相同的 null 判斷與預設值散在每個呼叫端。

````java
String name = (c == null) ? "occupant" : c.getName();
BillingPlan plan = (c == null) ? BillingPlan.BASIC : c.getPlan();
````

# Rule 7 - 【57 引入斷言】在程式碼中明確表達前置條件

- Level: `SHOULD`
- 目的：在程式碼中明確表達前置條件。
- 指令句：「用斷言明確寫出執行前必須成立的條件。」
- 適用時機：程式碼隱含某個「必須成立」的假設（例如數量必須是正數、某欄位此時必定已初始化），但只寫在註解或作者腦中。
- 操作步驟：
  1. 找出程式默默依賴、若不成立就是程式錯誤（bug）的條件。
  2. 在函式開頭用斷言寫出該條件（Java `assert` 或 `Objects.requireNonNull`、TypeScript 自訂 `assert(cond, msg)` 並宣告 `asserts cond`）。
  3. 斷言訊息說明違反的假設是什麼。
- 語言限制：Java 的 `assert` 預設在執行期停用（需 `-ea`），不可依賴它擋住正式環境的錯誤。
- 不適用或要小心：
  - 驗證使用者輸入或外部資料：那是可預期的錯誤，應用 62 快速失敗丟出明確例外，而不是斷言。
  - 斷言內含副作用（呼叫會改狀態的方法），停用斷言時行為會改變。

## Good Example

- 這個例子是好的，因為前置條件寫在程式碼裡，違反時立即暴露。

````typescript
function assert(cond: unknown, msg: string): asserts cond {
  if (!cond) throw new Error(`Assertion failed: ${msg}`);
}

function applyDiscount(rate: number): void {
  assert(rate > 0, "折扣率必須是正數");
  // ...
}
````

## Bad Example

- 這個例子是壞的，因為前置條件只在註解裡，違反時程式默默算出錯誤結果。

````typescript
// rate 一定是正數
function applyDiscount(rate: number): void {
  // ...
}
````

# Rule 8 - 【58 移除控制旗標】用明確的控制流程結束迴圈

- Level: `SHOULD`
- 目的：用明確的控制流程結束迴圈。
- 指令句：「把控制迴圈的旗標改成 break 或 return。」
- 適用時機：迴圈靠 `found`、`done` 之類的布林變數決定何時結束，旗標在迴圈中被設定、在條件中被檢查。
- 操作步驟：
  1. 找出設定旗標的位置。
  2. 若迴圈後只剩回傳結果，直接改成 `return`；否則改成 `break`（多層迴圈用 labeled break 或抽成函式後 return）。
  3. 刪除旗標變數及所有對它的檢查。
- 語言限制：無。
- 不適用或要小心：旗標在迴圈結束後仍被其他邏輯讀取，且無法用回傳值取代時，先抽函式再處理。

## Good Example

- 這個例子是好的，因為找到目標就直接返回，流程一目了然。

````java
String findMiscreant(List<String> people) {
    for (String p : people) {
        if (p.equals("Don") || p.equals("John")) {
            return p;
        }
    }
    return "";
}
````

## Bad Example

- 這個例子是壞的，因為讀者必須追蹤 found 在何時被設定、又在哪裡被檢查。

````java
boolean found = false;
String result = "";
for (String p : people) {
    if (!found) {
        if (p.equals("Don") || p.equals("John")) {
            result = p;
            found = true;
        }
    }
}
return result;
````

# Rule 9 - 【59 集合處理管線】將迴圈改成連續的集合操作

- Level: `SHOULD`
- 目的：將迴圈改成連續的集合操作。
- 指令句：「把 for 迴圈改寫成由 filter 和 map 組成的處理管線。」
- 適用時機：迴圈內是「跳過某些元素 → 轉換 → 收集」這類可拆成篩選、轉換、彙總的步驟。
- 操作步驟：
  1. 為迴圈的集合建立管線起點（Java `stream()`、TypeScript 陣列方法）。
  2. 把 `continue` 的條件改成 `filter`，把轉換改成 `map`，把累加改成 `reduce`／`collect`／`sum`。
  3. 每換一段就跑測試，最後刪除原迴圈。
- 語言限制：Java 8 以上（Stream API）；TypeScript／JavaScript 的陣列方法皆可。不支援的語言或版本不可套用。
- 不適用或要小心：
  - 迴圈中途需要 `break`／提早結束且無對應的短路操作（`find`、`some`、`anyMatch`、`takeWhile`）。
  - 迴圈內有檢查型例外（Java checked exception）或多個彼此依賴的可變狀態，硬改成管線會更難讀。
  - 在 lambda 中修改外部變數（副作用），這違反管線的用意，應保留迴圈或重新設計。

## Good Example

- 這個例子是好的，因為篩選、轉換、收集各成一段，意圖清楚。

````typescript
const indiaPhones = records
  .filter(r => r.country === "India")
  .map(r => r.phone);
````

## Bad Example

- 這個例子是壞的，因為篩選條件與收集邏輯混在迴圈體內，需要逐行追蹤。

````typescript
const indiaPhones: string[] = [];
for (const r of records) {
  if (r.country !== "India") continue;
  indiaPhones.push(r.phone);
}
````

# Rule 10 - 【60 查找表】用對照表取代一長串條件分支

- Level: `SHOULD`
- 目的：用對照表取代一長串條件分支。
- 指令句：「把冗長的 if / else if 改成查找表。」
- 適用時機：一長串 `if / else if` 或 switch 只是在「把某個鍵對應到某個值（或某個函式）」，各分支沒有其他邏輯。
- 操作步驟：
  1. 確認每個分支都只是「條件 → 結果」的純對應。
  2. 建立不可變的 Map／物件常數作為對照表。
  3. 以查表取代分支，並明確處理「查不到」的情況（預設值或丟例外，須與原本 else 行為一致）。
- 語言限制：無；TypeScript 可用 `Record<Enum, T>` 讓編譯器檢查鍵是否齊全。
- 不適用或要小心：
  - 分支條件是範圍或複合條件（`x > 10 && y < 3`），無法用單一鍵表示。
  - 分支內有各自不同的多步邏輯，此時考慮 54 多型或 61 策略模式。

## Good Example

- 這個例子是好的，因為對應關係集中在一張表，新增項目只改表格；查不到時回傳與原本 else 相同的預設值。

````typescript
const SHIPPING_FEE: ReadonlyMap<string, number> = new Map([
  ["north", 60],
  ["south", 80],
  ["east", 100],
]);
const DEFAULT_SHIPPING_FEE = 0;

const fee = SHIPPING_FEE.get(region) ?? DEFAULT_SHIPPING_FEE;
````

## Bad Example

- 這個例子是壞的，因為純粹的對應被寫成冗長分支，還夾帶魔術數字。

````typescript
let fee: number;
if (region === "north") fee = 60;
else if (region === "south") fee = 80;
else if (region === "east") fee = 100;
else fee = 0;
````

# Rule 11 - 【61 策略模式】讓不同的計算方式可以替換

- Level: `SHOULD`
- 目的：讓不同的計算方式可以替換。
- 指令句：「把選擇計算方式的分支改成策略模式。」
- 適用時機：同一個函式依條件選擇不同演算法（三角形／圓形／方形的計算、不同會員等級的計費方式），且演算法會隨需求增加或需要在執行期切換。
- 操作步驟：
  1. 定義策略介面（例如 `calculate()`）。
  2. 把每個分支的演算法搬成一個策略實作（Java 類別或 lambda；TypeScript 函式或物件）。
  3. 由呼叫端或設定注入（93 相依性注入）要使用的策略，移除選擇分支。
- 語言限制：無；支援一級函式的語言可直接用函式作為策略，不必建類別。
- 不適用或要小心：只有兩種計算方式且不會再增加，用簡單 if 更清楚（遵守 81 KISS、82 YAGNI）。

## Good Example

- 這個例子是好的，因為計費方式可替換，新增等級不必改既有程式碼。

````typescript
type PricingStrategy = (amount: number) => number;

const regular: PricingStrategy = a => a;
const gold: PricingStrategy = a => a * 0.9;
const vip: PricingStrategy = a => a * 0.8;

function checkout(amount: number, pricing: PricingStrategy): number {
  return pricing(amount);
}
````

## Bad Example

- 這個例子是壞的，因為每新增一種等級都得修改這個函式。

````typescript
function checkout(amount: number, level: string): number {
  if (level === "vip") return amount * 0.8;
  if (level === "gold") return amount * 0.9;
  return amount;
}
````

# Rule 12 - 【62 快速失敗】發現不合法的值就立即停止

- Level: `SHOULD`
- 目的：發現不合法的值就立即停止。
- 指令句：「一開始就驗證輸入，有錯就立即回報並停止。」
- 適用時機：不合法的輸入一路被傳到深處才出錯（NullPointerException、錯誤結果寫入資料庫），或錯誤被轉成「默默回傳預設值」。
- 操作步驟：
  1. 在公開函式或系統邊界（API、外部輸入）的開頭驗證所有輸入。
  2. 不合法時立即丟出含明確訊息的例外（`IllegalArgumentException`、自訂領域例外），不繼續執行。
  3. 搭配 51 守衛子句，讓驗證集中在函式開頭。
- 語言限制：無。
- 不適用或要小心：需求明確要求「容錯並繼續」（例如批次處理要跳過壞資料並彙整錯誤報告），此時應收集錯誤，而不是第一筆就停止；改成快速失敗前必須確認不會改變既有對外行為，否則屬於行為變更而非重構。

## Good Example

- 這個例子是好的，因為錯誤輸入在入口就被擋下，錯誤訊息指出原因。

````java
public void transfer(Account from, Account to, BigDecimal amount) {
    Objects.requireNonNull(from, "from 不可為 null");
    Objects.requireNonNull(to, "to 不可為 null");
    if (amount.signum() <= 0) {
        throw new IllegalArgumentException("轉帳金額必須大於 0：" + amount);
    }
    // 主流程
}
````

## Bad Example

- 這個例子是壞的，因為不合法金額被默默接受，錯誤延後到難以追查的地方才出現。

````java
public void transfer(Account from, Account to, BigDecimal amount) {
    if (from != null && to != null) {
        from.withdraw(amount); // 負數金額會變成存款
        to.deposit(amount);
    }
}
````

# Rule 13 - 【63 三元運算子】用一個運算式表達簡單分支

- Level: `SHOULD`
- 目的：用一個運算式表達簡單分支。
- 指令句：「把只用來決定指派值的簡短 if 改成三元運算子。」
- 適用時機：`if (cond) x = a; else x = b;` 這種兩個分支都只在指派同一個變數的簡短 if。
- 限制：
  - 僅限簡短指派：條件與兩個結果都應是單純運算式，整行讀起來一眼可懂。
  - 禁止巢狀三元運算子（`a ? b : c ? d : e`）；超過兩種結果改用 if、60 查找表或 69 模式比對。
  - 兩個分支內不可含副作用（呼叫會修改狀態的函式、`i++`）。
- 操作步驟：把 if／else 收斂成 `x = cond ? a : b;`，並讓 x 成為可宣告為 final／const 的變數。
- 語言限制：Java、TypeScript 皆支援；不支援三元運算子的語言（例如 Python 改用 `a if cond else b`、Go 無三元）依該語言慣用寫法，不可硬套。
- 不適用或要小心：分支內不只一個敘述，或結果運算式很長。

## Good Example

- 這個例子是好的，因為只是決定一個指派值，三元運算子讓變數可宣告為 const。

````typescript
const label = isOverdue ? "逾期" : "正常";
````

## Bad Example

- 這個例子是壞的，因為巢狀三元運算子讓讀者必須逐層拆解，應改用查找表或 if。

````typescript
const label = days > 30 ? "嚴重逾期" : days > 0 ? "逾期" : days === 0 ? "今日到期" : "正常";
````

# Rule 14 - 【64 德摩根定律】簡化含有否定的複合條件

- Level: `SHOULD`
- 目的：簡化含有否定的複合條件。
- 指令句：「用德摩根定律整理多重否定的條件式。」
- 適用時機：條件式出現 `!(A && B)`、`!(!A || !B)` 這類外層否定或雙重否定，閱讀時需要在腦中翻轉。
- 操作步驟：
  1. 套用 `!(A && B)` ⇔ `!A || !B`、`!(A || B)` ⇔ `!A && !B`。
  2. 消除雙重否定（`!!x`、`!isNotEmpty()` 改為正向命名）。
  3. 整理後若仍複雜，接著套用 52 拆解條件式。
  4. 改寫前後用測試或 74 決策表逐一比對條件組合，確保真值完全相同。
- 語言限制：無。
- 不適用或要小心：子條件有副作用，且轉換後短路順序會改變副作用是否執行。

## Good Example

- 這個例子是好的，因為移除外層否定，每個子條件都能直接讀懂。

````java
if (!user.isActive() || user.isLocked()) {
    denyAccess();
}
````

## Bad Example

- 這個例子是壞的，因為外層否定加內層否定，讀者要在腦中反轉兩次。

````java
if (!(user.isActive() && !user.isLocked())) {
    denyAccess();
}
````

# Rule 15 - 【65 可選鏈結】簡化逐層檢查 null 的巢狀判斷

- Level: `SHOULD`
- 目的：簡化逐層檢查 null 的巢狀判斷。
- 指令句：「把逐層檢查 null 的巢狀判斷改成可選鏈結。」
- 適用時機：`if (a != null) if (a.b != null) if (a.b.c != null)` 這類逐層 null 檢查。
- 操作步驟：
  1. 確認每一層的 null 判斷只是「為了安全取值」，沒有各自不同的處理。
  2. 改寫為 `a?.b?.c`，並確認結果為 `undefined`／`null` 時的後續處理與原本一致。
  3. 若呼叫鏈本身過長，同時評估 92 迪米特法則、43 隱藏委派，從根本縮短鏈。
- 語言限制：只在支援的語言／版本使用：
  - TypeScript 3.7 以上、JavaScript ES2020 以上、C# 6 以上、Kotlin、Swift 原生支援 `?.`。
  - Java 沒有 `?.`，等價寫法是 `Optional.ofNullable(a).map(A::getB).map(B::getC)`（Java 8 以上）；不可在 Java 原始碼寫 `?.`。
  - 專案的編譯目標或轉譯設定不支援時不可套用。
- 不適用或要小心：各層 null 代表不同的業務意義、需要不同處理（例如 a 為 null 要記錄錯誤），壓成一條鏈會吞掉差異。

## Good Example

- 這個例子是好的，因為可選鏈結取代逐層判斷，並用 ?? 明確指定預設值。

````typescript
const city = order?.customer?.address?.city ?? "未提供";
````

## Bad Example

- 這個例子是壞的，因為三層巢狀判斷只為了安全取一個值。

````typescript
let city = "未提供";
if (order != null) {
  if (order.customer != null) {
    if (order.customer.address != null) {
      city = order.customer.address.city ?? "未提供";
    }
  }
}
````

# Rule 16 - 【66 空值合併運算子】簡潔地指定空值時的預設值

- Level: `SHOULD`
- 目的：簡潔地指定空值時的預設值。
- 指令句：「用空值合併運算子 ?? 指定預設值。」
- 適用時機：`x != null ? x : 預設值`、或用 if 判斷空值後指派預設值的寫法。
- 操作步驟：
  1. 確認原本的判斷「只」針對 null／undefined。
  2. 改為 `x ?? 預設值`。
  3. 若原本用的是 `x || 預設值`，必須先確認 `0`、`""`、`false`、`NaN` 這些 falsy 值的原本處理：`||` 會把它們換成預設值，`??` 不會；兩者語意不同，替換前後行為必須一致。
- 語言限制：只在支援的語言／版本使用：
  - TypeScript 3.7 以上、JavaScript ES2020 以上、C#（`??` 自 C# 2 起、`??=` 自 C# 8 起）、PHP 7 以上、Kotlin 用 `?:`、Swift 用 `??`。
  - Java 沒有 `??`，等價寫法是 `Objects.requireNonNullElse(x, def)`（Java 9 以上）或 `Optional.ofNullable(x).orElse(def)`。
- 不適用或要小心：需要的是「falsy 時給預設值」（例如空字串也要換掉），此時應保留 `||` 或寫明確判斷，不可為了用 `??` 而改變行為。

## Good Example

- 這個例子是好的，因為只在 null／undefined 時套用預設值，數量 0 會被保留。

````typescript
const quantity = input.quantity ?? 1;
````

## Bad Example

- 這個例子是壞的，因為 `||` 會把合法的數量 0 換成 1，悄悄改變了行為。

````typescript
const quantity = input.quantity || 1;
````

# Rule 17 - 【67 列舉型別】避免狀態字串拼錯

- Level: `SHOULD`
- 目的：避免狀態字串拼錯。
- 指令句：「把代表狀態的字串改成列舉型別。」
- 適用時機：用 `"open"`／`"close"`／`"wait"` 這類字串或 0／1／2 數字代表狀態或種類，散落在比較與指派中。
- 操作步驟：
  1. 收集該欄位所有可能的值，建立列舉（`OPEN`、`CLOSED`、`WAITING`）。
  2. 在邊界（資料庫、JSON、API）做字串與列舉的轉換，內部一律使用列舉。
  3. 把字串比較改成列舉比較，讓編譯器協助檢查拼字與 switch 窮舉。
- 語言限制：Java 用 `enum`；TypeScript 可用 `enum` 或字串字面值聯集型別（`type Status = "open" | "closed" | "waiting"`），依專案慣例擇一。
- 不適用或要小心：值的集合是開放的、由外部動態決定（例如使用者自訂標籤），無法在編譯期列舉。
- 注意：序列化格式（存入資料庫或對外 API 的字串）不可因改用列舉而改變，否則屬於行為變更。

## Good Example

- 這個例子是好的，因為拼錯狀態名稱會在編譯期被擋下。

````java
enum OrderStatus { OPEN, CLOSED, WAITING }

if (order.getStatus() == OrderStatus.CLOSED) {
    archive(order);
}
````

## Bad Example

- 這個例子是壞的，因為 "close" 與 "closed" 的拼字差異只能在執行期才發現。

````java
if ("close".equals(order.getStatus())) {
    archive(order);
}
````

# Rule 18 - 【68 狀態模式】將各狀態的行為拆開

- Level: `SHOULD`
- 目的：將各狀態的行為拆開。
- 指令句：「用狀態模式整理依狀態切換的行為。」
- 適用時機：物件的多個方法都寫著 `switch (state)`，每種狀態（待命、執行中、完成）下同一個操作有不同行為。
- 操作步驟：
  1. 為狀態建立介面，宣告所有依狀態而異的操作。
  2. 每個狀態一個實作類別，搬入該狀態下的行為，並在其中決定轉換到哪個下一狀態。
  3. 原物件（context）持有目前狀態物件，把操作委派給它。
  4. 刪除原本各方法中的 `switch (state)`。
- 語言限制：無。
- 不適用或要小心：狀態很少、行為差異只在一兩個方法，用 67 列舉加簡單 switch 即可；若重點是「轉換規則」而非「各狀態行為」，改用 73 狀態機。

## Good Example

- 這個例子是好的，因為各狀態的行為與轉換各自封裝，新增狀態不必修改其他狀態。

````typescript
interface TaskState { start(task: Task): void; finish(task: Task): void; }

class Idle implements TaskState {
  start(task: Task) { task.setState(new Running()); }
  finish() { throw new Error("尚未開始，無法完成"); }
}
class Running implements TaskState {
  start() { throw new Error("已在執行中"); }
  finish(task: Task) { task.setState(new Done()); }
}
````

## Bad Example

- 這個例子是壞的，因為每個方法都重複依狀態分支，新增狀態要改遍所有方法。

````typescript
start() {
  switch (this.state) {
    case "idle": this.state = "running"; break;
    case "running": throw new Error("已在執行中");
    case "done": throw new Error("已完成");
  }
}
finish() {
  switch (this.state) { /* 又一份相同結構的 switch */ }
}
````

# Rule 19 - 【69 模式比對】讓依型別判斷的分支更容易讀

- Level: `SHOULD`
- 目的：讓依型別判斷的分支更容易讀。
- 指令句：「用模式比對改寫依型別分流的邏輯。」
- 適用時機：`if (x instanceof Circle) { Circle c = (Circle) x; ... } else if (x instanceof Square) ...` 這類依型別分流加強制轉型的寫法。
- 操作步驟：
  1. 確認被分流的型別集合（最好是 sealed／聯集型別，可讓編譯器做窮舉檢查）。
  2. 改寫為模式比對語法，並移除手動轉型。
  3. 若語言支援窮舉檢查，移除不必要的 default，讓新增型別時編譯器提示遺漏。
- 語言限制：只在支援的語言／版本使用：
  - Java：`instanceof` 模式比對需 Java 16 以上；`switch` 模式比對需 Java 21 以上；record 解構模式需 Java 21 以上；搭配 sealed interface（Java 17 以上）才有窮舉檢查。專案低於上述版本時不可套用。
  - TypeScript：沒有原生模式比對語法，用 discriminated union（共用 `kind` 欄位）＋ `switch` 收斂型別，並以 `never` 做窮舉檢查作為等價做法。
  - Kotlin `when`、C# 8 以上 `switch` 運算式、Scala、Rust 原生支援。
- 不適用或要小心：分流邏輯在多處重複，且行為屬於型別本身，應優先考慮 54 多型。

## Good Example

- 這個例子是好的，因為模式比對省去手動轉型，且 sealed 型別讓編譯器檢查是否漏掉案例（Java 21）。

````java
sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double s) implements Shape {}

double area(Shape shape) {
    return switch (shape) {
        case Circle c -> Math.PI * c.r() * c.r();
        case Square s -> s.s() * s.s();
    };
}
````

## Bad Example

- 這個例子是壞的，因為 instanceof 加強制轉型冗長，且新增型別時編譯器不會提醒。

````java
double area(Object shape) {
    if (shape instanceof Circle) {
        Circle c = (Circle) shape;
        return Math.PI * c.r() * c.r();
    } else if (shape instanceof Square) {
        Square s = (Square) shape;
        return s.s() * s.s();
    }
    return 0;
}
````

# Rule 20 - 【70 短路求值】結果確定時跳過後續判斷

- Level: `SHOULD`
- 目的：結果確定時跳過後續判斷。
- 指令句：「把成本較低的條件放前面，利用短路求值。」
- 適用時機：`&&`／`||` 條件中，昂貴的判斷（資料庫查詢、遠端呼叫、大量計算）放在便宜的判斷前面；或需要先檢查 null 才能安全存取的情況。
- 操作步驟：
  1. 評估每個子條件的成本與為真／為假的機率。
  2. `&&` 把便宜且最常為 false 的條件放前面；`||` 把便宜且最常為 true 的條件放前面。
  3. 依賴關係優先於成本：null 檢查等「保護後面條件安全」的子條件必須維持在前。
- 語言限制：Java、TypeScript 的 `&&`／`||` 皆為短路；Java 的 `&`／`|` 作用於 boolean 時不短路，不可混用。
- 不適用或要小心：
  - 子條件有副作用（寫入、計數、記錄日誌），調換順序會改變副作用是否發生，屬於行為變更，禁止調換。
  - 子條件會丟例外，調換後可能改變丟出哪個例外。

## Good Example

- 這個例子是好的，因為便宜的欄位檢查在前，大多數情況不必查資料庫。

````java
if (user.isActive() && permissionRepository.hasRole(user.getId(), "ADMIN")) {
    grant();
}
````

## Bad Example

- 這個例子是壞的，因為每次都先執行昂貴查詢，即使使用者早已停用。

````java
if (permissionRepository.hasRole(user.getId(), "ADMIN") && user.isActive()) {
    grant();
}
````

# Rule 21 - 【71 吞掉例外】留下錯誤資訊，避免問題被忽略

- Level: `MUST`
- 目的：留下錯誤資訊，避免問題被忽略。
- 指令句：「找出吞掉例外的地方，將例外資訊寫入日誌。」
- 性質：「吞掉例外」是要找出並修正的反模式，不是可以套用的手法；撰寫或重構時不可產生它。
- 偵測訊號見 `rules/程式碼異味掃描判準.md` 的補充規則，本條不重複列舉。
- 修正步驟：
  1. 至少用專案的 logger 記錄例外訊息、堆疊與足以重現的上下文（ID、參數）。
  2. 判斷此處是否真的能處理：不能處理就往上拋，或包成領域例外並保留原例外作為 cause。
  3. 確實要忽略的情況（例如關閉資源時的次要錯誤），必須在 catch 內以註解寫出忽略理由，並仍記錄 debug／warn 等級日誌。
  4. 捕捉範圍盡量縮小到具體例外型別，不用 `catch (Exception e)` 一網打盡。
- 不適用或要小心：
  - catch 內已以註解寫明忽略理由且有 debug／warn 等級日誌者，不屬於吞掉例外，不需修改。
  - 把「吞掉」改成「往上拋」會改變外部行為，屬於行為變更，必須另外確認；純重構時至少要補上日誌。

## Good Example

- 這個例子是好的，因為例外被記錄並保留原因，呼叫端能得知失敗。

````java
try {
    paymentGateway.charge(order);
} catch (GatewayTimeoutException e) {
    log.error("扣款逾時 orderId={}", order.getId(), e);
    throw new PaymentFailedException("扣款失敗：" + order.getId(), e);
}
````

## Bad Example

- 這個例子是壞的，因為扣款失敗被默默吞掉，系統會當作成功繼續出貨。

````java
try {
    paymentGateway.charge(order);
} catch (Exception e) {
    // ignore
}
````

# Rule 22 - 【72 移出迴圈不變程式碼】把結果固定的運算移到迴圈外

- Level: `SHOULD`
- 目的：把結果固定的運算移到迴圈外。
- 指令句：「把每輪結果都相同的運算移到迴圈外。」
- 適用時機：迴圈內有不依賴迴圈變數、每輪結果都相同的運算（重新編譯 regex、重複查詢設定、重新計算常數、`list.size()` 以外的昂貴呼叫）。
- 操作步驟：
  1. 確認該運算不依賴迴圈變數、也不依賴迴圈中會改變的狀態。
  2. 確認該運算沒有副作用，且呼叫次數改變不影響行為（例如不會影響計數、日誌或外部系統）。
  3. 把運算移到迴圈前，結果存入有名稱的 final／const 變數。
- 語言限制：無。
- 不適用或要小心：
  - 運算結果會隨時間或外部狀態改變（目前時間、隨機數、會被其他執行緒修改的值）。
  - 迴圈可能執行 0 次，而該運算有成本或會丟例外，移出後會在原本不執行的情況下被執行；此時需加上前置判斷或保留原位。

## Good Example

- 這個例子是好的，因為 regex 只編譯一次，迴圈內只做比對。

````java
final Pattern emailPattern = Pattern.compile(EMAIL_REGEX);
for (String input : inputs) {
    if (emailPattern.matcher(input).matches()) {
        valid.add(input);
    }
}
````

## Bad Example

- 這個例子是壞的，因為每一輪都重新編譯相同的 regex。

````java
for (String input : inputs) {
    if (Pattern.compile(EMAIL_REGEX).matcher(input).matches()) {
        valid.add(input);
    }
}
````

# Rule 23 - 【73 狀態機】明確定義各狀態如何轉換

- Level: `SHOULD`
- 目的：明確定義各狀態如何轉換。
- 指令句：「用狀態機整理多個旗標的組合與轉換。」
- 適用時機：物件用多個布林旗標（`isSubmitted`、`isApproved`、`isCancelled`）表達狀態，旗標組合中有不合法的組合（例如同時已核准又已取消），轉換規則散落各處。
- 操作步驟：
  1. 列出所有合法狀態（S1、S2、S3…），用 67 列舉表示，取代多個旗標。
  2. 列出合法轉換（從哪個狀態、經什麼事件、到哪個狀態），集中成一張轉換表。
  3. 所有狀態變更都經過單一轉換函式；不合法的轉換立即丟例外（62 快速失敗）。
  4. 為每個合法與不合法轉換寫測試。
- 語言限制：無。
- 不適用或要小心：只有一個布林旗標、只有兩種狀態且沒有轉換限制時，不需要狀態機。
- 與 68 狀態模式的分工：重點是「轉換規則」用狀態機；重點是「每個狀態下行為不同」用狀態模式；兩者可併用。

## Good Example

- 這個例子是好的，因為合法狀態與轉換集中定義，不可能出現矛盾的旗標組合。

````typescript
type Status = "draft" | "submitted" | "approved" | "cancelled";

const TRANSITIONS: Record<Status, Status[]> = {
  draft: ["submitted", "cancelled"],
  submitted: ["approved", "cancelled"],
  approved: [],
  cancelled: [],
};

function transition(from: Status, to: Status): Status {
  if (!TRANSITIONS[from].includes(to)) {
    throw new Error(`不合法的狀態轉換：${from} → ${to}`);
  }
  return to;
}
````

## Bad Example

- 這個例子是壞的，因為三個旗標有八種組合，其中多數不合法，卻沒有任何地方擋住。

````typescript
class Request {
  isSubmitted = false;
  isApproved = false;
  isCancelled = false;
  approve() { this.isApproved = true; } // 已取消也能核准
}
````

# Rule 24 - 【74 決策表】用表格檢查條件組合有沒有漏掉

- Level: `SHOULD`
- 目的：用表格檢查條件組合有沒有漏掉。
- 指令句：「用決策表逐一檢查條件組合與對應結果。」
- 適用時機：多個條件交織決定結果，難以確定每種組合都有被處理；或在套用 53 合併條件式、64 德摩根定律前後，需要確認真值沒有改變。
- 操作步驟：
  1. 列出所有影響結果的條件（A、B、C…），每個條件取 ○／✕。
  2. 展開所有組合（n 個布林條件共 2ⁿ 列），逐列填入目前程式碼產生的結果。
  3. 找出漏掉的組合、矛盾的組合、以及結果相同可合併的組合。
  4. 把決策表轉為參數化測試（JUnit `@ParameterizedTest`／`@CsvSource`、Jest `test.each`），作為重構前後的行為保護。
  5. 若表格本身清楚，可直接以 60 查找表實作。
- 語言限制：無。
- 不適用或要小心：條件數量過多導致組合爆炸（例如超過 5 個布林條件），應先用 52 拆解條件式分組，再對每組建表。

## Good Example

- 這個例子是好的，因為所有組合都列出並轉成測試，漏掉的情況一目了然。

````java
// 會員 | 滿額 | 折扣
//  ○   |  ○   | 20%
//  ○   |  ✕   | 10%
//  ✕   |  ○   | 5%
//  ✕   |  ✕   | 0%
@ParameterizedTest
@CsvSource({"true,true,20", "true,false,10", "false,true,5", "false,false,0"})
void discount(boolean member, boolean overThreshold, int expected) {
    assertEquals(expected, calc.discount(member, overThreshold));
}
````

## Bad Example

- 這個例子是壞的，因為巢狀 if 漏掉「非會員且未滿額」的情況，卻沒有任何檢查能發現。

````java
int discount(boolean member, boolean overThreshold) {
    if (member) {
        return overThreshold ? 20 : 10;
    } else if (overThreshold) {
        return 5;
    }
    throw new IllegalStateException(); // 非會員未滿額會走到這裡
}
````

# Rule 25 - 【75 尤達寫法】降低把比較誤寫成指派的機會

- Level: `SHOULD`
- 目的：降低把比較誤寫成指派的機會。
- 指令句：「把比較式統一成常數放左邊的尤達寫法。」
- 適用時機：所有「變數與常數或字面值」的相等比較。`if (x = 0)` 這類把比較誤寫成指派的錯誤，在 C、C++、PHP、JavaScript 中會被默默當成指派；改成 `if (0 == x)` 後，誤寫成 `0 = x` 會直接編譯失敗。
- 操作步驟：
  1. 找出所有常數或字面值在右邊的比較式。
  2. 統一把常數或字面值移到比較運算子左邊，同一專案不可混用兩種寫法。
  3. Java 的字串比較同樣把常數放左邊（`"open".equals(status)`），可一併避免 status 為 null 時的 NullPointerException。
- 語言限制：無特定語言限制。
- 不適用或要小心：兩邊都是變數時無法套用；專案的 Linter 明確禁止尤達寫法（例如 ESLint `yoda` 規則設為 never）時，不可自行放棄本招，也不可自行改 Linter 設定，必須回報使用者決定。

## Good Example

- 這個例子是好的，因為常數在左邊，漏打等號寫成 `0 = retryCount` 時會直接編譯失敗，不會默默變成指派。

````typescript
if (0 === retryCount) {
  giveUp();
}
````

## Bad Example

- 這個例子是壞的，因為常數在右邊，少打一個等號就變成指派且永遠為 false，不會有任何錯誤訊息。

````typescript
if (retryCount = 0) {
  giveUp();
}
````
