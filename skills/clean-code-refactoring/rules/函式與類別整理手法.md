# Rule 1 - 【26 抽取函式】有獨立用途的邏輯應抽成函式

- Level: `SHOULD`
- 目的：替一段完整的邏輯命名。
- 指令句：「把一段有獨立用途的邏輯抽成函式。」
- 適用時機：函式過長、需靠註解或空行分段才能閱讀；相同片段在多處重複；巢狀的內層可獨立成一個步驟；流程交錯、難以由上往下追蹤；某個片段大量使用其他類別的資料（先抽出該片段再移動）。
- 操作步驟：
  1. 找出能用一句話說明用途的程式碼片段（常見訊號：前面有註解、用空行分隔）。
  2. 依「做什麼」而非「怎麼做」為新函式命名。
  3. 找出片段使用的區域變數：只讀取的變成參數；片段內才宣告的留在新函式內；被片段修改且之後還會用到的，改成回傳值。
  4. 用呼叫新函式取代原片段，編譯並執行測試。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 片段會修改兩個以上外部仍需要的區域變數時，先用 32 拆分變數或 37 拆分處理階段整理，不要硬抽出多回傳值。
  - 抽出後需要很多參數時，表示切點不對，改考慮 30 抽取類別。
  - 與 31 內聯函式方向相反，判斷依據見該條。

## Good Example

- 抽出的函式名稱說明用途，主流程只讀名稱即可理解。

````java
void printOwing(Invoice invoice) {
    printBanner();
    BigDecimal outstanding = calculateOutstanding(invoice);
    printDetails(invoice, outstanding);
}
````

## Bad Example

- 所有細節混在一起，只能靠註解分段。

````java
void printOwing(Invoice invoice) {
    // banner
    System.out.println("****"); System.out.println("Customer Owes"); System.out.println("****");
    // 計算
    BigDecimal outstanding = BigDecimal.ZERO;
    for (Order o : invoice.orders()) outstanding = outstanding.add(o.amount());
    // 明細
    System.out.println("name: " + invoice.customer() + " amount: " + outstanding);
}
````

# Rule 2 - 【27 重新命名變數】變數名稱應反映它存的內容

- Level: `SHOULD`
- 目的：讓名稱反映變數的用途。
- 指令句：「把變數改成一看就知道它存什麼的名稱。」
- 適用時機：變數名稱看不出存放的內容（例如 `tmp`、`data`、`x`），或名稱與實際內容不符；32 拆分變數之後為各變數命名。
- 操作步驟：
  1. 確認變數實際存放的內容與單位（例如含稅或未稅、毫秒或秒）。
  2. 取一個說明內容的名稱，必要時帶上單位或狀態（`priceIncludingTax`、`timeoutMillis`）。
  3. 使用 IDE 的重新命名功能一次替換所有參照，編譯並執行測試。
- 語言限制：無特定語言限制；動態語言（JavaScript、Python）缺乏可靠的全域重新命名工具時，須以全文搜尋確認所有引用（含字串、設定檔）。
- 不適用或要小心：
  - 欄位名稱若與序列化（JSON 欄位、ORM 欄位對應）、反射、設定檔鍵值綁定，改名會改變外部行為；須同時調整對應設定或加上明確的對應註記（例如 `@JsonProperty`）。
  - 公開 API 的欄位改名屬於破壞性變更，須先用 47 封裝變數保留舊存取方式再遷移。
  - 作用範圍很小的慣用名稱（迴圈索引 `i`、lambda 的 `e`）不必改。

## Good Example

- 名稱說明內容是含稅價格。

````java
BigDecimal priceIncludingTax = basePrice.multiply(TAX_MULTIPLIER);
````

## Bad Example

- `tmp` 無法說明存的是什麼。

````java
BigDecimal tmp = basePrice.multiply(TAX_MULTIPLIER);
````

# Rule 3 - 【28 修改函式宣告】函式名稱與參數應符合函式用途

- Level: `SHOULD`
- 目的：讓名稱和參數符合函式用途。
- 指令句：「檢查並調整函式名稱和參數。」
- 適用時機：函式名稱看不出用途或只說了一半；參數過多、順序容易傳錯；函式依賴全域變數（改成由參數傳入）；用欄位在方法之間傳遞暫存值（改成參數）；有從未被用到的參數（移除）。
- 操作步驟：
  1. 呼叫端少、全在可控範圍內時：直接修改宣告並更新所有呼叫端。
  2. 呼叫端多或為公開 API 時採遷移法：
     - 先建立新宣告的函式，把舊函式本體搬過去。
     - 舊函式改為呼叫新函式，並標記 deprecated。
     - 逐步把呼叫端改用新函式，全部遷移後刪除舊函式。
  3. 每一步都編譯並執行測試。
- 語言限制：無特定語言限制；Java 沒有預設參數值，過渡期需以多載保留舊簽章；Kotlin、TypeScript、Python 可用預設參數值過渡。
- 不適用或要小心：
  - 有覆寫（override）或介面實作時，必須連同整個繼承階層一起改，否則會變成新增一個不相關的方法而非覆寫。
  - 移除參數前確認沒有呼叫端依賴它的副作用（例如參數運算式本身會觸發計算或 I/O）。
  - 對外公開的 API 不可直接改宣告，必須走遷移法。

## Good Example

- 名稱說明用途，參數明確。

````java
BigDecimal calculateShippingFee(Weight weight, Region destination) { /*...*/ }
````

## Bad Example

- 名稱與參數都看不出用途。

````java
BigDecimal calc(double a, String b) { /*...*/ }
````

# Rule 4 - 【29 抽取變數】複雜運算式應抽成有名稱的變數

- Level: `SHOULD`
- 目的：用名稱說明複雜運算式的含義。
- 指令句：「把長運算式抽成有明確名稱的變數。」
- 適用時機：運算式過長、讀者得自行拆解每段含義；子運算式有獨立含義卻沒有名稱；字面值只在單一運算式內有意義；條件式過長時與 52 拆解條件式並用。
- 操作步驟：
  1. 找出運算式中有獨立含義的子運算式。
  2. 宣告 `final`（或 `const`）區域變數保存子運算式結果，以其含義命名。
  3. 以變數取代原子運算式，編譯並執行測試。
  4. 若同一個子運算式在類別多個函式中都有意義，改用 26 抽取函式。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 子運算式有副作用或依賴求值時機（例如位於 `&&`、`||`、三元運算子的右側，原本可能不會被求值），抽成變數會改變求值次數或時機，進而改變行為；這種情況禁止抽成變數，改用 26 抽取函式。
  - 與 39 內聯變數方向相反，判斷依據見該條。

## Good Example

- 中間結果有名稱，運算式意義清楚。

````java
final BigDecimal basePrice = unitPrice.multiply(BigDecimal.valueOf(quantity));
final BigDecimal shippingFee = calculateShippingFee(order);
return basePrice.add(shippingFee);
````

## Bad Example

- 所有運算擠在一行，讀者需要自行拆解每段含義。

````java
return unitPrice.multiply(BigDecimal.valueOf(quantity)).add(calculateShippingFee(order));
````

# Rule 5 - 【30 抽取類別】同時負責兩件事的類別應拆成兩個類別

- Level: `SHOULD`
- 目的：拆開混在一起的職責。
- 指令句：「把同時負責兩件事的類別拆成兩個類別。」
- 適用時機：類別的欄位與方法可分成彼此少有往來的幾群；同一類別會因互不相關的原因被修改；一組值總是一起出現；領域概念以基本型別表示（建立值物件）；欄位只在特定情況下才有值；子類別只需要父類別的一部分（抽出後改用組合持有）；兩個類別互相存取內部細節（把共用部分抽成第三個類別）。
- 操作步驟：
  1. 依職責把欄位與方法分組（例如訂單中的「配送資訊」）。
  2. 建立新類別，原類別持有新類別的參照。
  3. 逐一以 36 移動函式與移動欄位把該組成員搬到新類別，每搬一個就編譯並測試。
  4. 檢查兩個類別的對外介面，決定新類別是否要對外公開或只在原類別內部使用。
- 語言限制：需支援類別或等價結構（Go 用 struct＋方法；TypeScript／JavaScript 可用 class 或模組＋物件）。
- 不適用或要小心：
  - 與 45 內聯類別方向相反，判斷依據見該條。
  - 拆出的類別若與原類別彼此雙向相依，表示切點不對（會產生 25 類別過度耦合）。
  - ORM 實體拆分會影響資料庫映射，需確認映射方式（例如 `@Embedded`）不改變資料表結構。

## Good Example

- 配送資訊獨立成類別，訂單持有它。

````java
class Order {
    private final Customer customer;
    private final Shipment shipment;
}
class Shipment { Address to; LocalDate date; BigDecimal fee() { /*...*/ } }
````

## Bad Example

- 訂單同時承擔顧客、訂單處理與配送三種職責。

````java
class Order {
    String customerName; String customerPhone;
    List<Item> items; BigDecimal total() { /*...*/ }
    String shipCity; String shipZip; LocalDate shipDate; BigDecimal shipFee() { /*...*/ }
}
````

# Rule 6 - 【31 內聯函式】本體與名稱一樣好懂的函式應內聯到呼叫端

- Level: `SHOULD`
- 目的：將多餘的函式包裝展開。
- 指令句：「如果函式本體和名稱一樣好懂，就把它內聯到呼叫端。」
- 適用時機：函式只是轉呼叫另一個函式；間接層沒有增加任何語意；類別裡只剩幾乎沒做事的小函式；也用於「先內聯、再以更好的切點重新 26 抽取」。
- 操作步驟：
  1. 確認函式沒有被子類別覆寫，也不是介面方法。
  2. 找出所有呼叫端，逐一以函式本體替換（參數換成對應引數）。
  3. 每替換一處就編譯並測試；全部替換後刪除原函式。
- 與 26 抽取函式的判斷依據（兩者方向相反）：
  - 讀名稱就能理解、而讀本體需要思考 → 保留函式（或執行 26 抽取）；取不出比本體更清楚的名字，就不要抽。
  - 本體一行且和名稱說的一樣清楚（例如 `isMoreThanFive() { return count > 5; }` 只在一處使用）→ 內聯。
  - 函式只是轉呼叫另一個函式、沒有增加語意 → 內聯。
  - 一群小函式切點錯亂、難以閱讀 → 先全部內聯，再依正確切點重新抽取。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 函式具多型性（被覆寫、實作介面）時不可內聯，否則會改變動態分派行為。
  - 本體含遞迴、多個 return，或在多處呼叫且內聯後會產生重複程式碼時，不要內聯。
  - 參數運算式有副作用時，內聯後若本體使用該參數多次，會造成重複求值。

## Good Example

- 名稱沒有比本體多提供資訊，直接內聯。

````java
int rating(Driver d) {
    return d.lateDeliveries() > 5 ? 2 : 1;
}
````

## Bad Example

- 多一層只包一行比較式的函式，閱讀時還得跳轉。

````java
int rating(Driver d) {
    return moreThanFiveLateDeliveries(d) ? 2 : 1;
}
boolean moreThanFiveLateDeliveries(Driver d) { return d.lateDeliveries() > 5; }
````

# Rule 7 - 【32 拆分變數】同時用於兩種用途的變數應拆開

- Level: `SHOULD`
- 目的：每個變數只負責一種用途。
- 指令句：「把同時用於兩種用途的變數拆開。」
- 適用時機：變數因為兼兩職而只能取籠統名稱；同一變數在流程中多處被改寫、讀者得來回對照才知道當下的值；也是 26 抽取函式的前置步驟。
- 操作步驟：
  1. 找出被賦值超過一次、且每次代表不同含義的變數（例如先存顯示用字串、後存計算用數值）。
  2. 在第一次賦值處改為新的、以用途命名的變數，並宣告為 `final`。
  3. 把到下一次賦值之前的參照改用新變數。
  4. 重複直到每個變數只有一種用途，每步編譯並測試。
- 語言限制：無特定語言限制；拆出的變數宜宣告為不可再指派（Java `final`、Kotlin `val`、TypeScript `const`）。
- 不適用或要小心：
  - 迴圈計數器、累加器（`sum += x`）、字串建構器屬於同一用途的多次賦值，不需拆分。
  - 參數被重新賦值也屬於此情況，應改用新區域變數，不要改寫參數。

## Good Example

- 每個變數只代表一種含義。

````java
final double perimeter = 2 * (height + width);
System.out.println(perimeter);
final double area = height * width;
System.out.println(area);
````

## Bad Example

- `temp` 先存周長、再存面積。

````java
double temp = 2 * (height + width);
System.out.println(temp);
temp = height * width;
System.out.println(temp);
````

# Rule 8 - 【33 引入參數物件】一組相關參數應包成物件

- Level: `SHOULD`
- 目的：把一組相關參數包成物件。
- 指令句：「把起始日和結束日包成一個參數物件。」
- 適用時機：參數過多；同一組參數（例如起始日與結束日）在多個函式的參數列中總是一起出現。
- 操作步驟：
  1. 找出總是一起出現的參數組（例如起始日、結束日）。
  2. 建立不可變的參數物件（Java `record`、TS `type`/`interface`），名稱說明這組值的概念（例如 `DateRange`）。
  3. 以 28 修改函式宣告加入新參數，呼叫端改傳參數物件，再移除原本的個別參數。
  4. 檢查原本散在函式內、針對這組值的運算（例如「日期是否在區間內」），以 36 移動函式搬進參數物件。
- 語言限制：無特定語言限制；參數物件寫法依語言而異：Java 16+ 用 `record`（16 以下手寫 final 欄位類別並實作 `equals`／`hashCode`）、Kotlin 用 `data class`、TypeScript 用 `interface`／`type`（僅編譯期型別，無執行期成本）、Python 用 `@dataclass`。
- 不適用或要小心：
  - 參數只是碰巧一起出現、沒有共同概念時，不要硬包，否則只是把參數列表藏起來。
  - 參數物件應不可變；若呼叫端原本依賴修改個別參數的副作用，需先確認語意。

## Good Example

- 起訖日包成具名的區間，區間相關判斷也放在裡面。

````java
record DateRange(LocalDate start, LocalDate end) {
    boolean contains(LocalDate d) { return !d.isBefore(start) && !d.isAfter(end); }
}
List<Reading> readingsIn(DateRange range);
````

## Bad Example

- 起訖日分開傳遞，容易傳反。

````java
List<Reading> readingsIn(LocalDate start, LocalDate end);
````

# Rule 9 - 【34 移除旗標參數】用布林旗標切換行為的函式應拆成兩個

- Level: `SHOULD`
- 目的：讓兩種操作各有清楚的名稱。
- 指令句：「把使用布林旗標切換行為的函式拆成兩個。」
- 適用時機：參數中有用來切換函式行為的布林旗標；呼叫端 `process(true)` 看不出意思。
- 操作步驟：
  1. 確認呼叫端傳入的旗標是字面值（`true` / `false`），而非執行期才決定的變數。
  2. 為每個旗標值建立一個具名函式（例如 `執行處理()`、`略過處理()`），內部呼叫原函式並固定旗標值。
  3. 把呼叫端改成呼叫具名函式。
  4. 所有呼叫端改完後，把原函式依旗標拆開或設為 private。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 旗標值多數來自執行期資料（例如設定、使用者輸入）時，拆開會讓呼叫端各自寫 `if`；此時可保留原函式供資料驅動使用，另外提供具名函式給字面值呼叫端。
  - 與 42 函式參數化的差別：42 傳入的是「資料值」（例如費率），保留單一函式；34 處理的是「切換行為的旗標」，應拆成兩個函式。

## Good Example

- 兩種操作各有清楚名稱。

````java
void bookRegular(Customer c, Concert show);
void bookPremium(Customer c, Concert show);
````

## Bad Example

- 呼叫端 `book(c, show, true)` 看不出 `true` 代表什麼。

````java
void book(Customer c, Concert show, boolean isPremium) {
    if (isPremium) { /* 高級座位流程 */ } else { /* 一般流程 */ }
}
````

# Rule 10 - 【35 分離查詢與更新】同時回傳值又修改狀態的函式應拆成兩個

- Level: `SHOULD`
- 目的：將回傳資料與改變狀態的操作分開。
- 指令句：「把同時回傳值又修改狀態的函式拆成兩個。」
- 適用時機：函式名稱看似查詢（`get`、`find`、`is`），卻同時修改狀態或觸發副作用；名稱因此誤導呼叫端、或讓流程難以追蹤時特別優先。
- 操作步驟：
  1. 複製原函式為純查詢版本，移除所有修改狀態的程式碼。
  2. 在原函式的每個呼叫端，改為先呼叫查詢函式取得值，再呼叫原函式。
  3. 把原函式的回傳值移除，改為只負責更新，並以更新語意重新命名。
  4. 每步編譯並執行測試。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 需要原子性的操作（例如 `queue.poll()`、`map.remove()` 回傳舊值、資料庫取號、CAS）不可拆開，否則在併發下查詢與更新之間會被其他執行緒插入，改變行為。
  - 查詢若成本高，拆開後呼叫端可能重複計算，需確認效能影響。

## Good Example

- 查詢與更新分開，查詢不會帶來副作用。

````java
Person findMiscreant(List<Person> people) { /* 只查詢 */ }
void alertForMiscreant(List<Person> people) { if (findMiscreant(people) != null) setOffAlarms(); }
````

## Bad Example

- 名稱像查詢，卻同時觸發警報。

````java
Person findMiscreant(List<Person> people) {
    for (Person p : people) if (p.isMiscreant()) { setOffAlarms(); return p; }
    return null;
}
````

# Rule 11 - 【36 移動函式】函式應移到它最常使用的資料所在位置

- Level: `SHOULD`
- 目的：讓函式靠近它主要操作的資料。
- 指令句：「把函式移到它最常使用的資料所在的位置。」
- 適用時機：函式取用其他類別的資料多於自身資料（最主要的情況）；同一概念的邏輯散落在多個類別；同一類別會因互不相關的原因被修改；類別只存資料、相關計算寫在外部；兩棵繼承樹必須成對擴充；父類別的方法只有部分子類別需要；兩個類別互相存取內部細節。
- 操作步驟：
  1. 檢查函式使用了哪些來源類別的成員，評估哪些也要一起搬。
  2. 在目標類別建立函式副本，把對來源物件的存取改成參數或目標類別自身成員。
  3. 讓來源函式改為委派給目標函式，編譯並測試。
  4. 逐一把呼叫端改為直接呼叫目標函式，最後視情況刪除來源函式（或保留為委派，見 43 隱藏委派）。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 函式在來源類別的繼承階層中有覆寫時，移動會改變多型行為，必須連同所有覆寫一起處理。
  - 函式大量使用兩個類別的資料時，先 26 抽取函式拆出依戀較重的部分再移動。
  - 搬到目標類別後若造成兩類別雙向相依，應重新評估。

## Good Example

- 帳戶透支費用的計算放在帳戶類型上，因為它主要使用帳戶類型的資料。

````java
class AccountType {
    BigDecimal overdraftCharge(int daysOverdrawn) {
        return isPremium ? PREMIUM_BASE.add(rate(daysOverdrawn)) : rate(daysOverdrawn);
    }
}
````

## Bad Example

- 函式放在 `Account`，卻主要取用 `AccountType` 的資料。

````java
class Account {
    BigDecimal overdraftCharge() {
        return type.isPremium() ? type.premiumBase().add(type.rate(daysOverdrawn)) : type.rate(daysOverdrawn);
    }
}
````

# Rule 12 - 【37 拆分處理階段】混在一起的處理應依順序拆成獨立階段

- Level: `SHOULD`
- 目的：依處理順序拆成獨立階段。
- 指令句：「把讀取與計算拆成兩個處理階段。」
- 適用時機：函式過長且前後做的是不同階段的事；同一段程式會因互不相關的原因被修改；流程交錯難以追蹤；常見於「解析輸入 + 業務計算 + 輸出格式」混在一起的程式。
- 操作步驟：
  1. 把第二階段（例如計算）的程式碼抽成函式。
  2. 定義一個中間資料結構，承載第一階段的產出。
  3. 讓第二階段函式只接收中間資料結構，不再直接存取原始輸入。
  4. 把第一階段（例如讀取、解析）抽成函式，回傳中間資料結構。
  5. 每步編譯並測試。
- 語言限制：無特定語言限制；階段間的中介資料結構可用 Java 16+ `record`、Kotlin `data class`、TypeScript `type` 表達。
- 不適用或要小心：
  - 讀取與計算本身需交錯進行（例如串流處理超大檔案、需邊讀邊判斷是否中止）時，拆成先讀完再算會改變記憶體用量與中止時機。
  - 中間資料結構應不可變，避免第二階段改寫第一階段的結果。

## Good Example

- 讀取與計算分開，計算只看中間資料。

````java
OrderData data = parseOrder(csvLine);
BigDecimal price = priceOrder(data, priceList);
````

## Bad Example

- 解析字串與計價混在同一段程式碼。

````java
String[] parts = csvLine.split(",");
int qty = Integer.parseInt(parts[1]);
BigDecimal price = priceList.get(parts[0]).multiply(BigDecimal.valueOf(qty));
````

# Rule 13 - 【38 將函式整合到類別】操作同一份資料的函式應整合到一個類別

- Level: `SHOULD`
- 目的：集中操作同一份資料的函式。
- 指令句：「把處理同一份資料的函式整合到一個類別。」
- 適用時機：一組函式總是傳入同一份資料；改一件事得同時動到散落各處的函式；類別只存資料、操作它的函式都在外部；多個函式共用一份全域資料；從大類別拆出的職責需要重新聚合。
- 操作步驟：
  1. 找出一組總是傳入同一份資料的函式（例如讀取、更新、刪除同一筆紀錄）。
  2. 以 47 封裝變數把共用資料封裝成類別的欄位。
  3. 逐一以 36 移動函式把函式搬進類別，並移除原本傳入資料的參數。
  4. 每步編譯並測試。
- 語言限制：需支援類別或等價結構（Go 用 struct＋方法；函數式寫法可改用模組＋閉包）。
- 不適用或要小心：
  - 函式雖然使用同一份資料，但各自屬於不同職責（例如顯示格式與持久化），整合後會產生 10 發散式變更，應分開。
  - 原本是純函式且被多處使用時，整合為實例方法後要確認不會引入共用可變狀態。

## Good Example

- 讀取、更新、刪除集中在資料管理類別。

````java
class ReadingStore {
    private final Map<String, Reading> data = new HashMap<>();
    Reading find(String id) { return data.get(id); }
    void update(Reading r)  { data.put(r.id(), r); }
    void delete(String id)  { data.remove(id); }
}
````

## Bad Example

- 操作同一份資料的函式散落各處，每次都要傳入資料。

````java
static Reading find(Map<String, Reading> data, String id) { /*...*/ }
static void update(Map<String, Reading> data, Reading r) { /*...*/ }
static void delete(Map<String, Reading> data, String id) { /*...*/ }
````

# Rule 14 - 【39 內聯變數】沒有額外語意的中間變數應換回原運算式

- Level: `SHOULD`
- 目的：去掉沒有額外意義的中間變數。
- 指令句：「把沒有額外語意的變數換回原運算式。」
- 適用時機：變數名稱沒有比運算式提供更多資訊（`tmp`、`result`、`value`）；變數妨礙 26 抽取函式等其他重構時。
- 操作步驟：
  1. 確認變數只被賦值一次，且賦值的運算式沒有副作用。
  2. 把變數的所有參照替換成原運算式（必要時加括號保持運算優先順序）。
  3. 刪除變數宣告，編譯並測試。
- 與 29 抽取變數的判斷依據（兩者方向相反）：
  - 變數名稱說明了運算式的業務含義（例如 `shippingFee`）→ 保留，或執行 29。
  - 變數名稱只是重述運算式或無意義（`tmp = a + b`）→ 內聯。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 運算式有副作用、成本高或結果會隨時間改變（例如 `now()`、讀取 I/O、遞增計數器）且變數被使用多次時，禁止內聯，否則會重複求值、改變行為。
  - 內聯時要保留運算子優先順序（`tmp = a + b; result = tmp * 2` 必須變成 `(a + b) * 2`）。

## Good Example

- 沒有語意的中間變數已移除，並保留括號。

````java
int result = (a + b) * 2;
````

## Bad Example

- `tmp` 沒有提供任何額外含義。

````java
int tmp = a + b;
int result = tmp * 2;
````

# Rule 15 - 【40 替換演算法】應以更簡單且結果相同的做法替換現有演算法

- Level: `SHOULD`
- 目的：以更簡單的方式得到相同結果。
- 指令句：「用更簡單、結果相同的演算法替換現有做法。」
- 適用時機：流程繞路、難以追蹤；函式因手寫的繁複流程而過長；繞路的手寫流程可由標準函式庫或更直接的寫法取代時。
- 操作步驟：
  1. 先用 26 抽取函式把要替換的演算法隔離在單一函式中。
  2. 確保有涵蓋邊界情況的測試（空集合、null、重複值、排序穩定性、極端值）；不足時先補特徵測試（招 76）。
  3. 撰寫新演算法，以相同測試驗證；必要時新舊並行比對輸出（招 99 黃金樣本測試）。
  4. 確認一致後才刪除舊演算法。
- 語言限制：無特定語言限制；改用標準函式庫較新的 API 時，須確認專案目標版本支援（例如 Java Stream 需 8+、`List.of` 需 9+）。
- 不適用或要小心：
  - 「結果相同」必須包含邊界行為：回傳 null 或空集合、例外類型、元素順序、浮點捨入方式；任一不同都屬於改變行為，禁止直接替換。
  - 新做法若明顯改變效能特性（時間或記憶體複雜度），需確認可接受。
  - 只替換一處演算法，不要同時混入其他重構。

## Good Example

- 用標準集合操作直接表達「找出第一個符合的名稱」。

````java
static final List<String> CANDIDATES = List.of("Don", "John", "Kent");
String foundPerson(List<String> people) {
    return people.stream().filter(CANDIDATES::contains).findFirst().orElse("");
}
````

## Bad Example

- 繞路的逐一比對流程。

````java
String foundPerson(List<String> people) {
    for (String p : people) {
        if (p.equals("Don")) return "Don";
        if (p.equals("John")) return "John";
        if (p.equals("Kent")) return "Kent";
    }
    return "";
}
````

# Rule 16 - 【41 移動陳述式】相關的程式碼應移到相鄰位置

- Level: `SHOULD`
- 目的：把相關的程式碼移到一起。
- 指令句：「調整陳述式的順序，讓相關的程式碼相鄰。」
- 適用時機：相關陳述式分散、彼此之間穿插不相干的邏輯；作為 26 抽取函式、55 拆分迴圈之前的準備步驟；變數宣告與第一次使用距離過遠時。
- 操作步驟：
  1. 找出操作同一資料或屬於同一步驟的陳述式。
  2. 檢查要移動的陳述式與它跨越的陳述式之間是否有相依：是否讀寫同一變數、是否呼叫有副作用的函式、是否可能丟出例外。
  3. 沒有相依時才移動，一次移動一小段，編譯並測試。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 跨越的陳述式會修改被移動陳述式使用的資料，或兩者都有 I/O、資料庫、日誌等副作用時，禁止交換順序，否則會改變行為。
  - 移過可能丟出例外的陳述式，會改變例外發生時已執行的副作用範圍。

## Good Example

- 只調整順序：定價相關的陳述式集中在一起，可接著抽成函式。

````java
Order order = loadOrder(id);
Customer customer = loadCustomer(order.customerId());

PricingPlan plan = pricingPlans.find(customer);
BigDecimal discount = plan.discountFor(order);
BigDecimal charge = order.subtotal().subtract(discount);

Warehouse warehouse = warehouses.nearestTo(customer);
LocalDate shipDate = warehouse.nextShipDate();
````

## Bad Example

- 定價相關的程式碼與不相干的出貨安排交錯。

````java
Order order = loadOrder(id);
Customer customer = loadCustomer(order.customerId());
PricingPlan plan = pricingPlans.find(customer);
Warehouse warehouse = warehouses.nearestTo(customer);
BigDecimal discount = plan.discountFor(order);
LocalDate shipDate = warehouse.nextShipDate();
BigDecimal charge = order.subtotal().subtract(discount);
````

# Rule 17 - 【42 函式參數化】只差數值的函式應合併並用參數傳入差異

- Level: `SHOULD`
- 目的：把只有固定值不同的函式合併。
- 指令句：「把只差數值的函式合併，用參數傳入差異。」
- 適用時機：多個函式的本體相同、只有常數不同；常數寫死在各自的函式中。
- 操作步驟：
  1. 從相似函式中選一個，以 28 修改函式宣告把差異的常數改為參數（例如 `rate`）。
  2. 將其他相似函式的呼叫端改為呼叫參數化後的函式，傳入原本的常數。
  3. 確認所有呼叫端都改完後，刪除舊函式。
  4. 每步編譯並測試。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 函式之間差異不只是數值，而是流程或行為（例如有一個多做一步驗證）時，不適用；改考慮 61 策略模式或 54 多型。
  - 與 34 移除旗標參數的差別：參數應傳入「資料值」，不可傳入用來切換行為的布林旗標，否則會製造出 34 要解決的問題。
  - 合併後若各呼叫端傳入的值有範圍限制，應以 57 引入斷言或 62 快速失敗寫明。

## Good Example

- 一個函式以參數接收費率。

````java
BigDecimal raise(BigDecimal salary, BigDecimal rate) {
    return salary.multiply(BigDecimal.ONE.add(rate));
}
````

## Bad Example

- 兩個函式只有費率常數不同。

````java
BigDecimal tenPercentRaise(BigDecimal s)  { return s.multiply(new BigDecimal("1.10")); }
BigDecimal fivePercentRaise(BigDecimal s) { return s.multiply(new BigDecimal("1.05")); }
````

# Rule 18 - 【43 隱藏委派】呼叫端應透過對外介面存取內部元件

- Level: `SHOULD`
- 目的：讓呼叫端透過對外介面操作。
- 指令句：「讓呼叫端透過中介物件存取，封裝內部元件。」
- 適用時機：呼叫端一層接一層取得深層物件（例如 `a.b().c().d()`）；呼叫端為了取得資料而必須知道物件內部結構時。
- 操作步驟：
  1. 在中介物件上為呼叫端需要的操作建立委派方法（例如 `person.manager()` 內部呼叫 `department.manager()`）。
  2. 把呼叫端改為呼叫委派方法，不再直接取得內部元件。
  3. 若不再有呼叫端需要內部元件，移除原本公開內部元件的 getter。
  4. 每步編譯並測試。
- 與 44 移除中間人的判斷依據（兩者方向相反）：
  - 呼叫端只用到內部元件的少數操作，且內部結構可能變動 → 隱藏委派。
  - 委派方法越加越多、又沒有提供封裝價值，中介物件變成只負責轉傳（命中 19 中間人）→ 改走 44。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 不要為了消除呼叫鏈而為內部元件的每個方法都建委派，那會直接造成 19 中間人。
  - Fluent API、Builder、Stream 的鏈式呼叫不適用此手法。

## Good Example

- 呼叫端只透過 `Person` 的對外介面操作。

````java
Person manager = person.manager();
````

## Bad Example

- 呼叫端直接穿過 `Person` 取得內部的 `Department`。

````java
Person manager = person.getDepartment().getManager();
````

# Rule 19 - 【44 移除中間人】只負責轉傳的中介方法應移除

- Level: `SHOULD`
- 目的：去掉只負責轉傳的中介層。
- 指令句：「移除只負責轉傳呼叫的中介方法。」
- 適用時機：類別的多數方法只是把呼叫原封不動轉給另一個物件；間接層沒有提供封裝、轉換等附加價值。
- 操作步驟：
  1. 在中介物件上提供取得被委派物件的方法（若尚未存在）。
  2. 把呼叫端從「呼叫委派方法」改為「取得被委派物件後直接呼叫」。
  3. 所有呼叫端改完後，刪除委派方法；若中介類別因此變空，再以 45 內聯類別處理。
  4. 每步編譯並測試。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 與 43 隱藏委派方向相反，判斷依據見該條。
  - 中介層若負責交易、權限、快取、日誌、轉換或防腐隔離，就不是單純轉傳，移除會改變行為或破壞架構邊界，禁止移除。

## Good Example

- 呼叫端直接使用真正做事的物件。

````java
Department dept = person.department();
Person manager = dept.manager();
List<Person> peers = dept.members();
````

## Bad Example

- `Person` 上堆滿只轉傳給 `Department` 的方法。

````java
class Person {
    Person manager()     { return department.manager(); }
    List<Person> peers() { return department.members(); }
    String budgetCode()  { return department.budgetCode(); }
}
````

# Rule 20 - 【45 內聯類別】職責過少的類別應併回使用端

- Level: `SHOULD`
- 目的：把職責過少的類別併回使用端。
- 指令句：「把幾乎空白的類別併入使用它的類別。」
- 適用時機：類別只剩一兩個簡單欄位或方法、且只被一處使用（最主要的情況）；類別只負責轉呼叫；類別是為未來預留、目前沒有作用的間接層；同一概念被拆成散落的小類別（併回）；也用於「先合併、再依正確職責重新 30 抽取類別」。
- 操作步驟：
  1. 在使用端類別建立被內聯類別所有公開方法與欄位的對應版本。
  2. 把對被內聯類別的呼叫改成呼叫使用端的新成員。
  3. 逐一以 36 移動函式把邏輯搬過來，每步編譯並測試。
  4. 被內聯類別沒有任何參照後刪除。
- 與 30 抽取類別的判斷依據（兩者方向相反）：
  - 類別代表明確領域概念（例如值物件 `Money`、`PhoneNumber`，承接 15 過度依賴基本型別），即使很小 → 保留（或執行 30）。
  - 類別只剩一兩個欄位且無行為、也不代表獨立領域概念（包含 30 抽取後切分過細的情況）→ 內聯，留在原類別。
- 語言限制：無特定語言限制。
- 不適用或要小心：
  - 被多個類別使用時，內聯會造成重複程式碼，應改為選擇最主要的使用端或保留。

## Good Example

- 幾乎空白的類別已併回唯一使用端。

````java
class Shipment {
    private String trackingCompany;
    private String trackingNumber;
    String trackingInfo() { return trackingCompany + ": " + trackingNumber; }
}
````

## Bad Example

- `TrackingInformation` 只被 `Shipment` 使用，且幾乎沒做事。

````java
class TrackingInformation { String company; String number; }
class Shipment {
    TrackingInformation tracking;
    String trackingInfo() { return tracking.company + ": " + tracking.number; }
}
````

# Rule 21 - 【46 工廠函式】物件的建立邏輯應集中到工廠函式

- Level: `SHOULD`
- 目的：集中物件的建立邏輯。
- 指令句：「把建立物件的邏輯集中到工廠函式。」
- 適用時機：多處重複相同的建立與初始化；依種類決定建立哪個子類別的分支散在各呼叫端；值物件的驗證與建立需要集中在一處。
- 操作步驟：
  1. 建立工廠函式（靜態方法或工廠類別），把建構子呼叫與初始化邏輯搬進去。
  2. 把所有直接呼叫建構子的地方改為呼叫工廠函式。
  3. 視需要把建構子改為 private，強制經由工廠建立。
  4. 若依種類建立不同子類別，把 switch 集中在工廠中，其他地方不再判斷種類。
- 語言限制：無特定語言限制；寫法依語言而異：Java 用 static 方法並將建構子設為 private，Kotlin 用 companion object 或頂層函式，TypeScript 用 `private constructor`＋static 方法；Java `record` 的標準建構子必須與 record 同等可見，無法設為 private，需改用一般類別或接受公開建構子。
- 不適用或要小心：
  - 只有一處建立、且建構子已足夠清楚時，不需要額外工廠（避免 20 過度泛化）。
  - 框架依賴無參數建構子或反射建立（ORM、序列化、DI 容器）時，建構子不可改為 private。

## Good Example

- 建立邏輯集中在工廠，呼叫端不必知道具體類別。

````java
static Employee create(String name, EmployeeType type) {
    return switch (type) {
        case ENGINEER -> new Engineer(name);
        case SALESPERSON -> new Salesperson(name);
        case MANAGER -> new Manager(name);
    };
}
````

## Bad Example

- 依種類建立物件的邏輯散在各呼叫端。

````java
Employee e;
if (type.equals("E")) e = new Engineer(name);
else if (type.equals("S")) e = new Salesperson(name);
else e = new Manager(name);
````

# Rule 22 - 【47 封裝變數】共用變數應只能透過函式讀寫

- Level: `SHOULD`
- 目的：集中變數的讀寫方式。
- 指令句：「讓共用變數只能透過函式讀寫。」
- 適用時機：可寫的全域或共用變數暫時無法消除；類別有公開 setter、外部可任意改寫；類別把可變的內部資料直接交給外部；也是 27 重新命名公開欄位、38 將函式整合到類別的前置步驟。
- 操作步驟：
  1. 建立讀取函式與（必要時）設定函式。
  2. 把所有直接存取變數的地方改為呼叫函式，每改一處就編譯並測試。
  3. 把變數的可見度降為 private。
  4. 若變數是集合或可變物件，讀取函式回傳不可變副本或唯讀檢視，修改改由明確的操作方法負責（例如 `addItem()`）。
- 語言限制：依語言而異：Java `record`、Kotlin `data class`（`val`）的欄位本身已唯讀，但集合欄位仍需回傳不可變副本（Java 10+ `List.copyOf`，舊版用 `Collections.unmodifiableList`）；TypeScript `readonly`／`private` 只在編譯期檢查，執行期仍可改寫（需真正封裝時用 `#` 私有欄位，ES2022+）；Python 無真正私有，只能以 `_` 前綴慣例搭配 `@property`。
- 不適用或要小心：
  - 讀取函式改為回傳副本後，若原本有呼叫端依賴「拿到參照後直接修改」的行為，會改變結果；需先找出這些呼叫端並改用明確的修改方法。
  - 在多執行緒環境，封裝不等於執行緒安全，需另外確認同步機制。

## Good Example

- 讀寫都經過受控函式，外部拿不到可變參照。

````java
class Owner {
    private final List<Item> items = new ArrayList<>();
    List<Item> items() { return List.copyOf(items); }
    void addItem(Item i) { items.add(Objects.requireNonNull(i)); }
}
````

## Bad Example

- 共用變數直接公開，任何地方都能改寫。

````java
class Owner {
    public List<Item> items = new ArrayList<>();
}
owner.items = null;
````

# Rule 23 - 【48 上移方法】子類別重複的方法應上移到父類別

- Level: `SHOULD`
- 目的：把子類別重複的方法移到父類別。
- 指令句：「把子類別中重複的方法上移到父類別。」
- 適用時機：兄弟子類別中出現內容相同的方法；合併成對擴充的繼承樹時，需要先把共同行為集中到父類別。
- 操作步驟：
  1. 比對各子類別中的方法，確認本體完全相同；只有細微差異時，先調整成相同（例如 42 函式參數化），再上移。
  2. 確認方法使用的欄位與呼叫的方法在父類別中也存在；沒有時先上移欄位或宣告抽象方法。
  3. 在父類別建立方法，刪除各子類別中的版本，編譯並測試。
- 語言限制：需支援繼承；Go 等無繼承語言不適用，改用嵌入 struct 或共用函式。
- 不適用或要小心：
  - 只有部分子類別擁有該方法時，上移會讓其他子類別繼承用不到的功能（造成 24 拒絕繼承），應考慮 49 抽取中間父類別或改用組合。
  - 子類別版本看似相同，但呼叫了各自覆寫的方法時，上移後行為仍依多型決定，要確認結果不變。

## Good Example

- 重複的方法只在父類別維護一份。

````java
abstract class Employee {
    protected String name;
    String displayName() { return name.toUpperCase(); }
}
class Engineer extends Employee {}
class Salesperson extends Employee {}
````

## Bad Example

- 兩個子類別各自寫一份相同方法。

````java
class Engineer extends Employee    { String displayName() { return name.toUpperCase(); } }
class Salesperson extends Employee { String displayName() { return name.toUpperCase(); } }
````

# Rule 24 - 【49 抽取父類別】相似類別的共同部分應抽到父類別

- Level: `SHOULD`
- 目的：把相似類別的共同行為集中起來。
- 指令句：「把兩個相似類別的共同部分抽到父類別。」
- 適用時機：兩個沒有繼承關係的類別有相同的欄位與方法；從過大的類別拆出的是與其他類別共通的行為；成對擴充的繼承樹之間有共同部分。
- 操作步驟：
  1. 建立空的父類別，讓相似類別繼承它。
  2. 逐一上移共同欄位、共同方法（48 上移方法），每步編譯並測試。
  3. 對只有部分相同的方法，先抽出相同部分（26 抽取函式）再上移，差異部分保留在子類別或宣告為抽象方法。
  4. 檢查呼叫端，能改用父類別型別的地方改用父類別型別。
- 語言限制：需支援繼承；Java、C# 為單一繼承，類別已有父類別時改用介面預設方法（Java 8+ `default`）或組合；Go 改用嵌入或介面；Java `record`、Kotlin `data class` 無法作為可繼承的父類別。
- 不適用或要小心：
  - 兩者不是「是一種」關係、只是剛好共用部分程式碼時，應改用 30 抽取類別並以組合共用，避免日後產生 24 拒絕繼承。
  - 目標語言只允許單一繼承時，若類別已有父類別，抽取父類別可能無法進行，改用組合或介面預設方法。
  - 與 50 攤平類別階層方向相反，判斷依據見該條。

## Good Example

- 共同欄位與行為集中在父類別。

````java
abstract class Party {
    protected final String name;
    Party(String name) { this.name = name; }
    String name() { return name; }
    abstract BigDecimal annualCost();
}
class Employee extends Party {
    private final BigDecimal monthlyCost;
    Employee(String name, BigDecimal monthlyCost) { super(name); this.monthlyCost = monthlyCost; }
    BigDecimal annualCost() { return monthlyCost.multiply(BigDecimal.valueOf(12)); }
}
class Department extends Party {
    private final List<Employee> staff;
    Department(String name, List<Employee> staff) { super(name); this.staff = List.copyOf(staff); }
    BigDecimal annualCost() {
        return staff.stream().map(Employee::annualCost).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}
````

## Bad Example

- 兩個類別各自維護相同欄位與相同的取名邏輯。

````java
class Employee   { String name; String name() { return name; } BigDecimal annualCost() { /*...*/ } }
class Department { String name; String name() { return name; } BigDecimal annualCost() { /*...*/ } }
````

# Rule 25 - 【50 攤平類別階層】沒有實質差異的父子類別應合併

- Level: `SHOULD`
- 目的：合併行為沒有差異的父子類別。
- 指令句：「把沒有實質差異的父類別和子類別合併。」
- 適用時機：抽象父類別只有一個子類別；父類別或子類別幾乎沒有內容；兩棵成對擴充的繼承樹可以合併；子類別幾乎用不到父類別功能、且父子差異不大。
- 操作步驟：
  1. 決定保留哪一個類別（通常保留名稱較貼近領域概念的那個）。
  2. 把要移除的類別中的欄位與方法上移或下移到保留的類別。
  3. 把所有參照被移除類別的型別宣告、`instanceof`、建構子呼叫改為保留的類別。
  4. 刪除空的類別，編譯並測試。
- 與 49 抽取父類別的判斷依據（兩者方向相反）：
  - 還有兩個以上子類別各自覆寫出不同行為，父類別承載實質的共同內容 → 不是「沒有實質差異」，保留階層（或執行 49），不可合併。
  - 父類別幾乎沒有共同內容，或唯一的子類別沒有加入任何差異 → 攤平（也因此不要用 49 建立這樣的父類別）。
- 語言限制：需支援繼承；Go 等無繼承語言不適用。
- 不適用或要小心：
  - 被移除的型別若出現在序列化資料、資料庫鑑別欄位（discriminator）、反射、對外 API 簽章中，合併會改變外部行為，必須先處理相容性。

## Good Example

- 唯一的子類別與父類別合併成一個類別。

````java
class Employee {
    private final String name;
    Employee(String name) { this.name = name; }
    BigDecimal salary() { /*...*/ }
}
````

## Bad Example

- 父類別只有一個子類別，子類別沒有加入任何差異。

````java
abstract class Employee { String name; abstract BigDecimal salary(); }
class Salesperson extends Employee { BigDecimal salary() { /*...*/ } } // 唯一子類別
````
