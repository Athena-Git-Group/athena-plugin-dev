# Rule 1 - 【90 程式碼覆蓋率】找出測試還沒跑到的程式碼

- Level: `MUST`
- 目的：找出測試還沒跑到的程式碼。
- 指令句：「重構前用程式碼覆蓋率找出測試缺口。」
- 階段：重構前（第一步）。
- 操作步驟：
  1. 用專案的覆蓋率工具（Java：JaCoCo；TypeScript：Vitest／Jest `--coverage`、c8／Istanbul）執行現有測試。
  2. 只看「本次要重構的範圍」的行覆蓋率與分支覆蓋率，標出未覆蓋的行與分支。
  3. 未覆蓋的部分，在重構前先用 Rule 2（76 特徵測試）或 Rule 3（99 黃金樣本測試）補上保護。
  4. 無法執行覆蓋率工具時，改以人工逐一列出重構範圍內的分支，並確認每個分支都有測試會走到。
- 禁止事項：
  - 不可在重構範圍覆蓋率不明的情況下直接開始修改。
  - 不可把「覆蓋率數字高」當成「行為已被保護」：被執行到但沒有斷言結果的程式碼，等同未保護。
- 無法補測試時：先向使用者說明風險（哪些行或分支沒有測試保護、重構後可能出現哪些無法察覺的行為改變），取得明確同意後才可繼續；取得同意前不修改產品程式碼。

## Good Example

- 這個例子是好的，因為重構前先量出缺口，並針對未覆蓋分支補測試。

````md
1. 執行 `./gradlew test jacocoTestReport`
2. 重構範圍 `PricingService.calc()`：行覆蓋 72%，分支覆蓋 50%
3. 未覆蓋：`if (coupon.isExpired())` 的 true 分支、`region == null` 分支
4. 先補兩支特徵測試，覆蓋確認後才開始重構
````

## Bad Example

- 這個例子是壞的，因為只看整體數字就開始改，重構範圍的分支其實沒被測到。

````md
1. 專案整體覆蓋率 80%，應該夠了
2. 直接開始拆 `PricingService.calc()`
````

# Rule 2 - 【76 特徵測試】先記錄程式目前的行為

- Level: `MUST`
- 目的：先記錄程式目前的行為。
- 指令句：「重構前先用特徵測試鎖定既有行為。」
- 階段：重構前。
- 操作步驟：
  1. 針對 Rule 1 找出的測試缺口，呼叫目標程式碼並取得「目前實際的」輸出，而不是「應該要的」輸出。
  2. 把實際輸出寫成斷言（先寫一個必定失敗的斷言，從失敗訊息讀出實際值，再填回去）。
  3. 涵蓋正常值、邊界值（0、空、null、最大值）、錯誤輸入與每一個分支。
  4. 若發現目前行為看似 bug，仍以目前行為為準寫入測試並加註記；修 bug 是另一個獨立的變更，不可混在重構中。
- 禁止事項：
  - 缺少測試保護的程式碼不可直接重構。
  - 不可在撰寫特徵測試的同時修改產品程式碼。
- 無法補時：同 Rule 1，先向使用者說明風險並取得明確同意後才可繼續。

## Good Example

- 這個例子是好的，因為測試鎖定的是目前實際行為，包括看起來可疑的結果。

````java
@Test
void characterize_shippingFee() {
    assertEquals(60, legacy.shippingFee("north", 999));
    assertEquals(0, legacy.shippingFee("north", 1000));
    // 目前行為：未知地區回傳 -1（疑似 bug，另開單處理，重構期間保持不變）
    assertEquals(-1, legacy.shippingFee("unknown", 500));
}
````

## Bad Example

- 這個例子是壞的，因為測試寫的是「應該要的」行為，並順手修了 bug，重構前後無法比較。

````java
@Test
void shippingFee() {
    assertEquals(60, legacy.shippingFee("north", 999));
    // 順便把 -1 改成丟例外
    assertThrows(IllegalArgumentException.class, () -> legacy.shippingFee("unknown", 500));
}
````

# Rule 3 - 【99 黃金樣本測試】以既有輸出為基準比對完整結果

- Level: `SHOULD`
- 目的：以既有輸出為基準比對完整結果。
- 指令句：「用黃金樣本比對重構前後的完整輸出。」
- 階段：重構前（建立基準），重構中與重構後（比對）。
- 適用時機：輸出龐大或結構複雜、難以逐一斷言的程式（報表、匯出檔、產生的 HTML／JSON、批次處理結果、SQL 產生器），或缺乏單元測試的舊系統。
- 操作步驟：
  1. 準備具代表性的固定輸入集（含邊界與異常資料）。
  2. 在重構前執行，把完整輸出存成黃金樣本檔並納入版控。
  3. 每次重構後以相同輸入執行，與黃金樣本逐字比對，有差異就標出並視為失敗。
  4. 排除不穩定欄位（時間戳、隨機 ID、雜湊順序），以固定時鐘、固定亂數種子或比對前正規化處理。
- 限制：
  - 黃金樣本只能在「確認是刻意的行為變更」時更新，不可為了讓測試通過而直接覆蓋樣本。
  - 黃金樣本證明的是「沒變」，不是「正確」；與 Rule 2 特徵測試互補。

## Good Example

- 這個例子是好的，因為以完整輸出比對，且排除了不穩定的時間欄位。

````typescript
test("月報輸出與黃金樣本一致", () => {
  const output = generateMonthlyReport(fixtureOrders, { clock: fixedClock("2026-01-31") });
  const golden = readFileSync("test/golden/monthly-report.csv", "utf8");
  expect(output).toBe(golden);
});
````

## Bad Example

- 這個例子是壞的，因為只檢查有沒有輸出，任何欄位或排序的改變都不會被發現。

````typescript
test("月報可以產生", () => {
  const output = generateMonthlyReport(fixtureOrders);
  expect(output.length).toBeGreaterThan(0);
});
````

# Rule 4 - 【98 Mikado 方法】釐清大型變更的相依順序

- Level: `SHOULD`
- 目的：釐清大型變更的相依順序。
- 指令句：「先用 Mikado 方法畫出變更相依關係，再依序修改。」
- 階段：重構前（規劃修改順序）。
- 適用時機：變更會牽動多個檔案或模組、一改就連鎖編譯錯誤、無法一次完成的大型重構。
- 操作步驟：
  1. 寫下最終目標作為根節點（例如「把 OrderService 拆成三個服務」）。
  2. 直接嘗試實作目標；遇到編譯失敗或測試失敗時，把「必須先完成的前置條件」記為子節點。
  3. 立即回退（git restore / stash）剛才的嘗試，回到乾淨可編譯的狀態。
  4. 對每個子節點重複步驟 2–3，直到找出不再有前置條件的葉節點。
  5. 從葉節點開始，一次完成一個節點，每完成一個就編譯、測試、提交，再往根節點前進。
- 限制：探索階段不可保留「改到一半、無法編譯」的程式碼；圖要寫下來（文字樹或清單），不只放在腦中。
- 不適用或要小心：只牽動單一函式或單一檔案的小重構，直接用 Rule 7（77 小步修改）即可。

## Good Example

- 這個例子是好的，因為先畫出相依樹再從葉節點開始，每一步都可編譯可提交。

````md
目標：OrderService 改用 PaymentGateway 介面
├─ 抽出 PaymentGateway 介面
│   └─ 把 StripeClient 的靜態呼叫改為實例方法   ← 葉節點，先做
└─ OrderService 改為建構子注入
    └─ 修正 3 個直接 new OrderService() 的測試   ← 葉節點，先做
````

## Bad Example

- 這個例子是壞的，因為直接硬改，連鎖錯誤越改越多，最後無法回到可編譯狀態。

````md
1. 把 OrderService 改成用介面 → 37 個編譯錯誤
2. 逐一修錯誤，修到一半又冒出新錯誤
3. 兩天後仍無法編譯，只好整包丟棄
````

# Rule 5 - 【89 認知複雜度】量化程式碼有多難理解

- Level: `SHOULD`
- 目的：量化程式碼有多難理解。
- 指令句：「優先重構認知複雜度高的函式。」
- 階段：重構前（決定優先順序）。
- 操作步驟：
  1. 用工具量測認知複雜度（Java：SonarQube／SonarLint 規則 S3776；TypeScript：`eslint-plugin-sonarjs` 的 `cognitive-complexity`）。
  2. 依分數由高到低排序重構範圍內的函式，高者優先處理。
  3. 補充參考值（原圖未給數值門檻）：單一函式 15 以上視為需要重構（SonarQube 預設值）；專案有自訂門檻時以專案為準。
  4. 認知複雜度主要來自巢狀與中斷流程，優先套用 51 守衛子句、52 拆解條件式、26 抽取函式、58 移除控制旗標。
- 與 88 環狀複雜度的差異：環狀複雜度數「路徑數」（影響需要幾個測試），認知複雜度數「理解難度」（巢狀越深加權越重）；排序優先順序看認知複雜度，強制拆分門檻看 Rule 6。
- 無工具時：以巢狀層數（超過 3 層，對應異味 04）與中斷流程數量人工估計。

## Good Example

- 這個例子是好的，因為依量化分數排序，先處理最難懂的函式。

````md
認知複雜度（eslint sonarjs/cognitive-complexity）：
- applyPromotion()  31  ← 優先
- buildInvoice()    18
- formatAddress()    4  ← 不處理
````

## Bad Example

- 這個例子是壞的，因為依個人感覺挑選，最難懂的函式反而沒處理。

````md
先重構 formatAddress()，因為它看起來命名不太好；applyPromotion() 太長了之後再說。
````

# Rule 6 - 【88 環狀複雜度】量化程式的分支複雜度

- Level: `MUST`
- 目的：量化程式的分支複雜度。
- 指令句：「把環狀複雜度超過 10 的函式拆開。」
- 階段：重構前（判定必須拆分的對象），重構後（確認已降到門檻內）。
- 門檻：單一函式環狀複雜度超過 10，必須拆分。
- 補充參考值（原圖只規定超過 10 的函式要拆開）：新撰寫的程式碼也以不超過 10 為準。
- 計算方式：1 ＋ 分支點數量（`if`、`else if`、`case`、`for`、`while`、`catch`、`&&`、`||`、`?:` 各加 1）。
- 操作步驟：
  1. 用工具量測（Java：PMD `CyclomaticComplexity`、Checkstyle `CyclomaticComplexity`、SonarQube；TypeScript：ESLint 內建 `complexity` 規則設為 10）。
  2. 超過 10 的函式，依其分支性質選手法：26 抽取函式、51 守衛子句、60 查找表、54 多型、61 策略模式。
  3. 拆分後重新量測，確認每個函式都在 10 以內，且行為由測試保護（環狀複雜度即最少所需測試路徑數，可用來檢查 Rule 1 的分支覆蓋是否足夠）。
- 例外：由框架或產生器產生、不手動維護的程式碼（例如自動產生的 parser）可排除，但須在報告中註明。

## Good Example

- 這個例子是好的，因為量測後超標的函式被拆開，且有工具守住門檻。

````md
ESLint：complexity: ["error", 10]
- validateForm() 複雜度 14 → 拆成 validateContact()（5）、validatePayment()（6）、validateForm()（3）
- 重新量測全部 ≤ 10，測試全數通過
````

## Bad Example

- 這個例子是壞的，因為超過門檻卻以「能動就好」為由保留。

````md
- validateForm() 複雜度 14
- 結論：功能正常，先不拆
````

# Rule 7 - 【77 小步修改】有問題時能快速定位是哪一步

- Level: `MUST`
- 目的：有問題時能快速定位是哪一步。
- 指令句：「每次只做一小步修改，維持原本的行為。」
- 階段：重構中。
- 操作步驟：
  1. 一次只套用一個重構手法（例如只做一次 26 抽取函式），不同手法分開進行。
  2. 每一步完成後必須可編譯、測試全過（Rule 8），再進行下一步。
  3. 每一步完成後建議提交（commit），commit 訊息寫明套用的手法編號。
  4. 某一步失敗時，回退該步（而不是繼續往前修），重新評估手法或把步驟切得更小。
- 禁止事項：
  - 不可在同一步中同時重構與修改行為（修 bug、加功能、改需求）；行為變更必須是獨立的步驟與提交。
  - 不可一次修改大量檔案後才第一次執行測試。
  - IDE 自動重構（Rename、Extract Method）同樣算一步，完成後仍要跑測試。

## Good Example

- 這個例子是好的，因為每一步只做一件事，任一步出錯都能精準回退。

````md
commit 1：refactor(51) checkout() 改用守衛子句          ✓ 測試通過
commit 2：refactor(26) 抽出 calcShipping()              ✓ 測試通過
commit 3：refactor(27) tmp 改名為 taxIncludedPrice      ✓ 測試通過
````

## Bad Example

- 這個例子是壞的，因為重構與行為修改混在一起，測試失敗時無法判斷是哪個改動造成。

````md
commit 1：重寫 checkout()（拆函式、改命名、順便修運費計算錯誤、加新折扣）
         ✗ 12 個測試失敗
````

# Rule 8 - 【78 回歸測試】找出改動意外破壞的功能

- Level: `MUST`
- 目的：找出改動意外破壞的功能。
- 指令句：「每完成一個改動，就執行完整的回歸測試。」
- 階段：重構中（每一步之後）。
- 操作步驟：
  1. 開始重構前，先確認專案的編譯與完整測試指令（依專案建置設定而定，例如 `./gradlew test`、`mvn test`、`npm test`）可執行且全數通過。
  2. 每完成 Rule 7 的一小步，就執行編譯與完整的回歸測試（完整測試套件，含特徵測試與黃金樣本測試），不可只跑與修改範圍相關的部分測試。
  3. 任何測試失敗：回退該步，不可修改測試的期望值來讓它通過（除非證明該測試本身有錯，且需另外說明）。
- 禁止事項：
  - 不可略過、停用（`@Disabled`、`.skip`）或刪除失敗的測試來讓結果通過。
  - 不可在測試未全過的狀態下進行下一步。
  - 不可只憑「看起來沒問題」或「編譯通過」宣告重構完成。

## Good Example

- 這個例子是好的，因為失敗時回退並縮小步驟，而不是修改測試。

````md
步驟 4（36 移動函式）後執行完整測試：1 個失敗（InvoiceTest.rounding）
→ git restore，回到步驟 3
→ 改為先抽出 roundAmount()，再移動，測試全過後提交
````

## Bad Example

- 這個例子是壞的，因為為了讓測試通過而修改期望值，等於接受了被破壞的行為。

````md
步驟 4 後 InvoiceTest.rounding 失敗：期望 100.5，實際 100
→ 把期望值改成 100，測試通過，繼續下一步
````

# Rule 9 - 【96 絞殺榕模式】逐步以新功能取代舊功能

- Level: `SHOULD`
- 目的：逐步以新功能取代舊功能。
- 指令句：「用絞殺榕模式逐步從舊實作切換到新實作。」
- 階段：重構中（大規模替換時）。
- 適用時機：要整個替換舊模組、舊 API、舊系統，無法在一次小步內完成，且替換期間系統必須持續可運作。
- 操作步驟：
  1. 在舊實作前建立一個切換點（介面、facade、路由、feature flag）。
  2. 讓新實作與舊實作並存（舊 → 舊＋新），一次只把一部分功能或流量切到新實作。
  3. 每切換一部分，用 Rule 3 黃金樣本或並行比對（同時呼叫新舊、比較結果）確認一致。
  4. 所有功能都切換完成並穩定後，才刪除舊實作與切換點（舊＋新 → 新）。
- 限制：
  - 不可一次性大爆炸式替換（big bang rewrite）。
  - 切換點必須能快速切回舊實作。
  - 並存期間須有明確的移除計畫，避免新舊兩套永久並存（變成異味 02 重複程式碼）。
- 不適用或要小心：替換範圍只有單一函式或類別時，直接用 Rule 7 小步修改即可。

## Good Example

- 這個例子是好的，因為以切換點逐步遷移，每一步都可回退。

````java
class TaxCalculatorRouter implements TaxCalculator {
    public Money calc(Order o) {
        return featureFlags.isOn("new-tax", o.region())
            ? newCalculator.calc(o)
            : legacyCalculator.calc(o);
    }
}
// 第 1 週：north 切新版；第 2 週：south；全區穩定後刪除 legacyCalculator 與 router
````

## Bad Example

- 這個例子是壞的，因為一次替換整個模組，出問題時無法部分回退。

````md
1. 刪除 LegacyTaxCalculator，全部改呼叫 NewTaxCalculator
2. 一次上線所有地區
3. south 稅額錯誤，只能整包回滾
````

# Rule 10 - 【85 單元測試】逐一驗證每個單元的行為

- Level: `MUST`
- 目的：逐一驗證每個單元的行為。
- 指令句：「替拆分出來的每個函式撰寫單元測試。」
- 階段：重構後。
- 操作步驟：
  1. 列出本次重構新產生的函式、類別（抽取函式、抽取類別、策略實作、狀態類別等）。
  2. 為每一個撰寫單元測試，涵蓋正常值、邊界值與錯誤輸入；有分支者至少覆蓋每個分支（數量參考 Rule 6 的環狀複雜度）。
  3. 測試名稱描述行為（`returnsZeroWhenCartIsEmpty`），一個測試驗證一個行為。
  4. 單元測試不依賴資料庫、網路、時間等外部資源；需要時用相依性注入（93）替換。
- 禁止事項：
  - 不可只依賴上層整合測試或特徵測試就結束，拆出來的單元必須有自己的測試。
  - 不可寫沒有斷言、或只斷言「不拋例外」的空殼測試。
- 例外：私有輔助函式若已被其公開呼叫端的單元測試完整覆蓋，可不單獨測試，但須能指出覆蓋它的測試。

## Good Example

- 這個例子是好的，因為拆出來的函式各自有測試，涵蓋正常與邊界情況。

````typescript
describe("calcShipping", () => {
  test("滿 1000 免運", () => expect(calcShipping(1000)).toBe(0));
  test("未滿 1000 收 60", () => expect(calcShipping(999)).toBe(60));
  test("金額為負時丟出錯誤", () => expect(() => calcShipping(-1)).toThrow());
});
````

## Bad Example

- 這個例子是壞的，因為測試沒有任何斷言，只證明函式能被呼叫。

````typescript
test("calcShipping", () => {
  calcShipping(500);
});
````

# Rule 11 - 【86 Linter】自動找出程式碼中的問題

- Level: `SHOULD`
- 目的：自動找出程式碼中的問題。
- 指令句：「修正 Linter 回報的所有警告。」
- 階段：重構後。
- 操作步驟：
  1. 執行專案設定的 Linter（Java：Checkstyle、PMD、SpotBugs、SonarLint；TypeScript：ESLint、`tsc --noEmit`）。
  2. 修正 Linter 回報的所有錯誤與警告，包含修改前就已存在的警告。
  3. 既有警告的修正與重構手法分開進行，每修正一類警告視為獨立的一小步。
  4. 修正 Linter 警告也屬於修改，修完必須再跑 Rule 8 的回歸測試。
- 限制：
  - 不可用停用註解（`// eslint-disable`、`@SuppressWarnings`）壓掉警告了事；確實是誤報時，停用範圍要縮到最小（單行、單一規則）並寫明理由。
  - 不可為了消除警告而修改 Linter 設定，除非使用者同意。

## Good Example

- 這個例子是好的，因為修正警告的根本原因，誤報時僅局部停用並說明。

````typescript
// 修正前：'result' is assigned a value but never used → 刪除未使用變數
// 確定為誤報的單一處：
// eslint-disable-next-line @typescript-eslint/no-non-null-assertion -- 上一行已用 has() 確認存在
const handler = handlers.get(type)!;
````

## Bad Example

- 這個例子是壞的，因為整個檔案停用 Linter，所有問題都被隱藏。

````typescript
/* eslint-disable */
````

# Rule 12 - 【87 程式碼格式化工具】自動統一縮排與空白

- Level: `SHOULD`
- 目的：自動統一縮排與空白。
- 指令句：「用格式化工具統一程式碼格式。」
- 階段：重構後。
- 操作步驟：
  1. 使用專案既有的格式化工具與設定（Java：Spotless、google-java-format、IDE 共用設定；TypeScript：Prettier、`eslint --fix`）。
  2. 只格式化本次修改的檔案或範圍。
  3. 格式化後確認 diff 中只剩實質修改與該檔案的格式調整。
- 限制：
  - 不可在同一個 commit 中混合「大範圍格式化」與「邏輯重構」；若需要整檔或整專案重新格式化，獨立成一個 commit，讓審查者能分開檢視。
  - 不可自行引入與專案不同的格式化設定。
- 專案沒有格式化工具時：遵循檔案中既有的縮排與空白風格，並向使用者建議導入工具，不自行新增設定。

## Good Example

- 這個例子是好的，因為格式化與邏輯修改分開提交，審查時一目了然。

````md
commit 1：style: 套用 Prettier 格式化 order/ 目錄（純格式，無邏輯變更）
commit 2：refactor(26) 抽出 calcShipping()
````

## Bad Example

- 這個例子是壞的，因為整個專案重新格式化和邏輯修改混在同一個 commit，真正的修改被淹沒。

````md
commit 1：refactor checkout（檔案變更 214 個，其中 211 個只有縮排差異）
````

# Rule 13 - 【84 童軍法則】每次修改都順手改善一點

- Level: `SHOULD`
- 目的：每次修改都順手改善一點。
- 指令句：「用童軍法則，順手整理這次有動到的程式碼。」
- 階段：重構後（收尾）。
- 操作步驟：
  1. 在本次修改過的檔案與函式範圍內，順手處理小型、低風險的改善：27 重新命名變數、82 YAGNI（直接刪除）無用程式碼、80 DRY 原則（把魔術數字改成具名常數）、修正 Linter 警告。
  2. 每個順手改善仍遵守 Rule 7 小步修改與 Rule 8 回歸測試。
  3. 範圍外發現的較大問題，記錄下來回報使用者，不在本次處理。
- 限制：
  - 只整理「這次有動到」的程式碼，不可藉機擴大重構範圍到無關檔案。
  - 順手改善不可改變行為，也不可與本次主要修改混在同一個 commit 而難以審查。
  - 沒有測試保護的區域不做順手改善。

## Good Example

- 這個例子是好的，因為只在本次修改的函式內做小改善，並把範圍外的問題記錄下來。

````md
本次修改：OrderService.cancel()
順手整理：
- cancel() 內 `flag` 改名為 `isRefundable`
- 刪除 cancel() 內未使用的變數 `oldStatus`
範圍外發現（未處理，已回報）：
- PaymentService 有重複的退款計算邏輯
````

## Bad Example

- 這個例子是壞的，因為以童軍法則為名擴大範圍，把無關模組也一起重寫。

````md
本次修改：OrderService.cancel()
順便也重構了：PaymentService、ReportService、UserController（共 23 個檔案）
````
