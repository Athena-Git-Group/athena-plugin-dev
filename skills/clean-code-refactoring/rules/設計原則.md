# Rule 1 - 【79 單一職責原則】讓每個元件各自負責一件事

- Level: `SHOULD`
- 目的：讓每個元件各自負責一件事。
- 指令句：「依照單一職責原則，把元件按職責拆開。」
- 撰寫時遵守：
  - 每個函式、類別、模組只有一個「會讓它需要修改的理由」（一個需求來源、一個使用角色）。
  - 動手前先用一句話描述元件的職責；描述中出現「和」「並且」「同時」時，代表應該拆開。
  - 設定、資料存取、計算、輸出等不同性質的工作分屬不同元件。
- 違反時的辨識訊號：
  - 類別名稱含 Manager、Helper、Util、Processor 等籠統字眼，且方法彼此不相關。
  - 一個類別同時 import 資料庫、HTTP、檔案 I/O 與格式化相關套件。
  - 不同需求的修改總是碰到同一個檔案。
- 違反時對應手法：30 抽取類別、26 抽取函式、36 移動函式。
- 不適用或要小心：拆分後各元件只有一兩行且永遠一起變動，過度拆分會變成異味 21 閒置類別。

## Good Example

- 這個例子是好的，因為計算、儲存、通知各自獨立，任一需求改變只動一個類別。

````java
class InvoiceCalculator { Money total(Invoice inv) { /* 計算 */ } }
class InvoiceRepository { void save(Invoice inv) { /* 儲存 */ } }
class InvoiceNotifier   { void send(Invoice inv) { /* 寄信 */ } }
````

## Bad Example

- 這個例子是壞的，因為計算規則、資料庫結構、信件格式任何一個改變都要修改同一個類別。

````java
class InvoiceService {
    Money total(Invoice inv) { /* 計算 */ }
    void save(Invoice inv) { /* JDBC */ }
    void send(Invoice inv) { /* SMTP + HTML 範本 */ }
}
````

# Rule 2 - 【80 DRY 原則】讓同一條規則只維護一份

- Level: `SHOULD`
- 目的：讓同一條規則只維護一份。
- 指令句：「依照 DRY 原則，將相同的知識或規則集中到一處。」
- 撰寫時遵守：
  - 同一條業務規則（稅率、驗證規則、狀態轉換、格式）只在一處定義，其他地方引用它。
  - 寫第二份相似程式碼前，先搜尋是否已有可重用的函式或常數。
  - DRY 針對的是「知識」重複，不是「長得像」的程式碼：兩段程式碼外觀相同但代表不同業務規則、會各自演進時，不要強行合併。
- 違反時的辨識訊號：
  - 修一個 bug 需要在多處做相同修改，或曾經「改了一處漏了另一處」。
  - 前後端、多個服務各自寫一份相同的驗證規則且未共用來源。
- 違反時對應手法：26 抽取函式、42 函式參數化、48 上移方法、56 引入特殊案例、60 查找表。
- 不適用或要小心：為了消除重複而引入的抽象，比重複本身更難理解或耦合了不相關的模組（違反 81 KISS）。

## Good Example

- 這個例子是好的，因為營業稅率只定義一次，調整時只改一處。

````typescript
export const VAT_RATE = 0.05;
export const withVat = (amount: number): number => amount * (1 + VAT_RATE);
````

## Bad Example

- 這個例子是壞的，因為同一條稅率規則分散在多處，調整稅率時很容易漏改。

````typescript
const cartTotal = subtotal * 1.05;
const invoiceTotal = invoiceAmount * 1.05;
const refund = paid / 1.05;
````

# Rule 3 - 【81 KISS 原則】避免不必要的複雜度

- Level: `SHOULD`
- 目的：避免不必要的複雜度。
- 指令句：「依照 KISS 原則，採用最簡單的做法。」
- 撰寫時遵守：
  - 在滿足目前需求的前提下，選擇讀者最容易理解的做法；優先使用語言與標準函式庫的內建功能。
  - 不為了展示技巧而使用設計模式、反射、泛型體操或過度巧妙的單行寫法。
  - 能用一般函式解決就不建立類別階層；能用 if 解決就不引入策略模式。
- 違反時的辨識訊號：
  - 環狀複雜度或認知複雜度偏高（見 `安全重構流程.md` 的 88、89 門檻）。
  - 需要畫圖或長篇註解才能解釋一段簡單功能的流程。
  - 一個需求的實作跨越過多層抽象（介面、工廠、抽象工廠、設定檔）。
- 違反時對應手法：40 替換演算法、31 內聯函式、45 內聯類別、50 攤平類別階層、44 移除中間人。
- 不適用或要小心：需求本身就複雜（例如並行、交易一致性），此時應讓複雜度集中且被隔離，而不是假裝簡單。

## Good Example

- 這個例子是好的，因為直接使用標準函式庫，一行就清楚表達意圖。

````java
boolean hasAdmin = users.stream().anyMatch(User::isAdmin);
````

## Bad Example

- 這個例子是壞的，因為為了一個簡單判斷引入了不必要的抽象層。

````java
UserPredicateFactory factory = UserPredicateFactoryProvider.getInstance().create();
UserMatcher matcher = new UserMatcher(factory.forRole(Role.ADMIN));
boolean hasAdmin = new UserCollectionScanner(users).scan(matcher).isNotEmpty();
````

# Rule 4 - 【82 YAGNI】先做目前需要的功能

- Level: `SHOULD`
- 目的：先做目前需要的功能。
- 指令句：「依照 YAGNI 原則，先省略目前用不到的擴充。」
- 撰寫時遵守：
  - 只實作目前需求明確要求的功能；「以後可能會用到」不是撰寫程式碼的理由。
  - 不預留沒有呼叫端的參數、設定開關、擴充點、抽象介面（只有一個實作且沒有測試替身需求的介面）。
  - 需要擴充時再透過重構加入（100 開放封閉原則是在「確定有變化點」時才套用）。
- 違反時的辨識訊號：
  - 參數永遠傳同一個值、設定項永遠是預設值、介面只有一個實作、抽象父類別只有一個子類別。
  - 程式碼中有 `// TODO: 未來支援 XX` 而對應的分支或欄位已寫好卻沒被使用。
- 違反時對應手法：82 YAGNI（直接刪除）、31 內聯函式、45 內聯類別、50 攤平類別階層。
- 不適用或要小心：對外公開的 API／資料格式一旦發布難以變更（例如資料庫 schema 的版本欄位、API 版本號），此類低成本的前瞻設計可以保留，但需註明理由。

## Good Example

- 這個例子是好的，因為目前只需要匯出 CSV，就只實作 CSV。

````typescript
function exportOrders(orders: Order[]): string {
  return toCsv(orders);
}
````

## Bad Example

- 這個例子是壞的，因為為了不存在的需求預留格式參數與外掛機制，全都沒有呼叫端。

````typescript
function exportOrders(
  orders: Order[],
  format: "csv" | "xlsx" | "pdf" = "csv",
  plugins: ExportPlugin[] = [],
): string {
  if (format !== "csv") throw new Error("尚未支援");
  return plugins.reduce((out, p) => p.apply(out), toCsv(orders));
}
````

# Rule 5 - 【83 關注點分離】拆開介面、處理邏輯與資料

- Level: `SHOULD`
- 目的：拆開介面、處理邏輯與資料。
- 指令句：「依照關注點分離原則，拆開介面、邏輯和資料。」
- 撰寫時遵守：
  - 介面層（Controller、UI 元件、CLI）只負責接收輸入、呼叫邏輯、呈現結果。
  - 處理邏輯層（Service、領域物件、純函式）不依賴 HTTP、UI 框架或資料庫細節。
  - 資料層（Repository、API client）只負責存取資料，不包含業務判斷。
  - 補充（原圖未提及）：前端元件中，畫面呈現與資料取得、狀態邏輯分開（例如 Nuxt／Vue 用 composable 承接邏輯）。
- 違反時的辨識訊號：
  - Controller 裡有 SQL 或業務計算；Service 裡出現 `HttpServletRequest`、`Response` 或 DOM 操作；Repository 裡有 if 判斷業務規則。
  - 無法在不啟動框架或資料庫的情況下測試業務邏輯。
- 違反時對應手法：37 拆分處理階段、30 抽取類別、36 移動函式、93 相依性注入。
- 不適用或要小心：一次性腳本或極小型工具，分層的成本大於效益時可合併，但業務計算仍建議抽成獨立函式。

## Good Example

- 這個例子是好的，因為 Controller 只處理介面，邏輯與資料存取各自分層。

````java
@PostMapping("/orders/{id}/cancel")
public ResponseEntity<Void> cancel(@PathVariable long id) {
    orderService.cancel(id);
    return ResponseEntity.noContent().build();
}

// OrderService：業務規則；OrderRepository：資料存取
````

## Bad Example

- 這個例子是壞的，因為介面、業務規則與 SQL 全部混在 Controller，無法單獨測試業務規則。

````java
@PostMapping("/orders/{id}/cancel")
public ResponseEntity<Void> cancel(@PathVariable long id) {
    Map<String, Object> row = jdbc.queryForMap("SELECT * FROM orders WHERE id=?", id);
    if ("SHIPPED".equals(row.get("status"))) return ResponseEntity.badRequest().build();
    jdbc.update("UPDATE orders SET status='CANCELLED' WHERE id=?", id);
    return ResponseEntity.noContent().build();
}
````

# Rule 6 - 【91 型別註記】避免把不同型別的值混用

- Level: `SHOULD`
- 目的：避免把不同型別的值混用。
- 指令句：「為函式參數和回傳值加上型別註記。」
- 撰寫時遵守：
  - 公開函式的參數與回傳值一律寫出型別；區域變數可依賴型別推論。
  - 補充（原圖未提及）：TypeScript 以 strict 模式撰寫，禁止使用 `any`；不確定的外部資料用 `unknown` 搭配型別收斂或執行期驗證。
  - 用專用型別表達領域概念（金額、ID、電話號碼），避免全部用 string／number（對應異味 15）。
  - 避免不必要的型別斷言（`as`、強制轉型）；需要時把斷言集中在邊界並說明理由。
- 違反時的辨識訊號：
  - TypeScript 出現 `any`、隱含 any、`// @ts-ignore`；Java 使用 raw type（`List` 而非 `List<Order>`）或 `Map<String, Object>` 傳遞結構化資料。
  - 函式接受 `userId: string` 與 `orderId: string`，呼叫時參數順序對調也不會報錯。
- 違反時對應手法：28 修改函式宣告、33 引入參數物件、30 抽取類別（把基本型別封裝成專用型別）。
- 不適用或要小心：語言本身為動態型別且專案未導入型別檢查工具時，改以文件或執行期驗證補足，不強制註記。

## Good Example

- 這個例子是好的，因為參數、回傳值都有明確型別，外部資料以 unknown 進入再驗證。

````typescript
type OrderId = string & { readonly __brand: "OrderId" };

function findOrder(id: OrderId): Promise<Order | undefined> { /* ... */ }

function parseOrder(raw: unknown): Order {
  if (!isOrder(raw)) throw new Error("訂單格式錯誤");
  return raw;
}
````

## Bad Example

- 這個例子是壞的，因為 any 讓編譯器放棄檢查，錯誤只能在執行期發現。

````typescript
function findOrder(id: any): any { /* ... */ }

const order = findOrder(123) as any;
order.totl.toFixed(2); // 拼錯欄位也不會報錯
````

# Rule 7 - 【92 迪米特法則】只和直接認識的物件互動

- Level: `SHOULD`
- 目的：只和直接認識的物件互動。
- 指令句：「依照迪米特法則，只呼叫直接相關的物件。」
- 撰寫時遵守：
  - 一個方法只呼叫：自身、自己的欄位、傳入的參數、自己建立的物件上的方法。
  - 不透過「朋友的朋友」取得物件再操作（`a.getB().getC().doSomething()`）；改為請直接認識的物件代為完成（「告訴它做，不要問它要」）。
  - 流暢介面（builder、Stream 管線）回傳的是同一類物件，不算違反。
- 違反時的辨識訊號：
  - 呼叫端知道對方的內部結構，對方內部一改，呼叫端就跟著壞。
  - 測試時需要層層 mock 才能建立一個物件。
- 違反時對應手法：43 隱藏委派、36 移動函式、65 可選鏈結（只是治標，仍應評估是否縮短鏈）。
- 不適用或要小心：純資料結構（DTO、record、設定物件）的屬性存取，沒有行為可封裝時，深層存取可以接受；過度隱藏委派會產生異味 19 中間人，需取得平衡。

## Good Example

- 這個例子是好的，因為呼叫端只要求訂單提供它需要的結果，不需知道內部結構。

````java
String city = order.shippingCity();
````

## Bad Example

- 這個例子是壞的，因為呼叫端穿過三層物件，任何一層結構變動都會影響它。

````java
String city = order.getCustomer().getAddress().getCity().getName();
````

# Rule 8 - 【93 相依性注入】讓外部元件更容易替換

- Level: `SHOULD`
- 目的：讓外部元件更容易替換。
- 指令句：「用相依性注入傳入外部相依項目。」
- 撰寫時遵守：
  - 元件所依賴的外部資源（資料庫、HTTP client、時鐘、亂數、檔案系統、訊息佇列）從建構子或參數傳入，不在內部 `new` 或呼叫靜態單例取得。
  - 優先使用建構子注入，並宣告為 final／readonly；Spring 中避免欄位注入（`@Autowired` 在欄位上）。
  - 依賴抽象介面而非具體實作，以便測試時注入替身。
- 違反時的辨識訊號：
  - 業務程式碼中出現 `new JdbcTemplate(...)`、`HttpClient.newHttpClient()`、`LocalDateTime.now()`、`Math.random()`、`XxxHolder.getInstance()`。
  - 單元測試必須連線真實資料庫或網路，或需要靜態 mock 工具才能測試。
- 違反時對應手法：28 修改函式宣告（把相依改為參數）、47 封裝變數、46 工廠函式。
- 不適用或要小心：不會變動且沒有副作用的值物件或純工具函式（如 `Math.max`、字串處理），不需要注入。

## Good Example

- 這個例子是好的，因為時鐘與儲存庫由外部注入，測試時可替換成固定時間與記憶體實作。

````java
class SubscriptionService {
    private final SubscriptionRepository repo;
    private final Clock clock;

    SubscriptionService(SubscriptionRepository repo, Clock clock) {
        this.repo = repo;
        this.clock = clock;
    }

    boolean isExpired(long id) {
        return repo.find(id).expiresAt().isBefore(Instant.now(clock));
    }
}
````

## Bad Example

- 這個例子是壞的，因為相依項目寫死在內部，測試無法控制時間，也無法隔離資料庫。

````java
class SubscriptionService {
    private final SubscriptionRepository repo = new JdbcSubscriptionRepository();

    boolean isExpired(long id) {
        return repo.find(id).expiresAt().isBefore(Instant.now());
    }
}
````

# Rule 9 - 【94 純函式】相同輸入會得到相同輸出

- Level: `SHOULD`
- 目的：相同輸入會得到相同輸出。
- 指令句：「把計算邏輯抽成沒有副作用的純函式。」
- 撰寫時遵守：
  - 計算、轉換、驗證、格式化等邏輯寫成純函式：只依賴參數，不讀寫外部狀態，不修改傳入的參數，不做 I/O。
  - 把副作用（資料庫、網路、日誌、時間、亂數）推到外層，核心計算保持純粹（functional core, imperative shell）。
  - 需要時間或亂數時，以參數傳入，而不是在函式內取得。
- 違反時的辨識訊號：
  - 函式同時回傳值又修改狀態（手法 35 所處理的情況）。
  - 同一個函式用相同參數呼叫兩次結果不同；函式內同時有計算與 `save()`／`log()`／`fetch()`。
  - 測試計算邏輯需要準備資料庫或 mock 外部服務。
- 違反時對應手法：26 抽取函式、35 分離查詢與更新、37 拆分處理階段、93 相依性注入。
- 不適用或要小心：本質就是副作用的操作（寫檔、送出請求）不需要也無法變成純函式；重點是把其中的計算部分抽出來。

## Good Example

- 這個例子是好的，因為計算部分是純函式，可直接用輸入輸出測試；副作用留在外層。

````typescript
const calcLateFee = (dueDate: Date, today: Date, dailyFee: number): number => {
  const days = Math.max(0, daysBetween(dueDate, today));
  return days * dailyFee;
};

async function chargeLateFee(loanId: string): Promise<void> {
  const loan = await repo.find(loanId);
  const fee = calcLateFee(loan.dueDate, new Date(), DAILY_FEE);
  await repo.addFee(loanId, fee);
}
````

## Bad Example

- 這個例子是壞的，因為計算混合了取得目前時間與修改傳入物件，結果不可預測也難以測試。

````typescript
function calcLateFee(loan: Loan): number {
  const days = daysBetween(loan.dueDate, new Date());
  loan.fee = days * globalConfig.dailyFee; // 修改參數又讀全域設定
  return loan.fee;
}
````

# Rule 10 - 【95 不可變資料】避免資料被就地改寫

- Level: `SHOULD`
- 目的：避免資料被就地改寫。
- 指令句：「使用不可變資料，有更新時建立新值。」
- 撰寫時遵守：
  - 變數預設宣告為 final（Java）或 const（TypeScript）；確實需要重新指派時才放寬。
  - 值物件、DTO 優先使用 Java record、不可變類別（無 setter、欄位 final），或 TypeScript `readonly` 屬性與 `ReadonlyArray`。
  - 更新時建立新物件（`{ ...obj, status: "done" }`、`withStatus(...)`），而不是修改原物件。
  - 對外回傳集合時回傳不可變檢視或複本（`List.copyOf`、`Collections.unmodifiableList`），避免呼叫端改到內部狀態。
- 違反時的辨識訊號：
  - 一個變數被用於多種用途（手法 32 所處理的情況）。
  - 物件被傳進函式後內容被改變，呼叫端不知情；排序、過濾直接修改原陣列（`array.sort()`、`splice`）。
  - 多執行緒共用可變物件，需要大量 synchronized。
- 違反時對應手法：47 封裝變數、32 拆分變數、35 分離查詢與更新。
- 不適用或要小心：經量測證實大量複製造成效能問題的熱點（例如大型矩陣運算、緩衝區），可在局部封裝範圍內使用可變資料，但不可外洩。

## Good Example

- 這個例子是好的，因為更新時建立新值，原本的資料不受影響。

````typescript
interface Task { readonly id: string; readonly status: "todo" | "done"; }

const complete = (task: Task): Task => ({ ...task, status: "done" });

const sorted = [...tasks].sort(byDueDate);
````

## Bad Example

- 這個例子是壞的，因為函式就地修改傳入物件與陣列，其他持有同一參照的程式會被意外影響。

````typescript
function complete(task: Task): void {
  task.status = "done";
}

tasks.sort(byDueDate); // 原陣列被改掉
````

# Rule 11 - 【97 命名規則】讓程式碼使用一致的命名方式

- Level: `SHOULD`
- 目的：讓程式碼使用一致的命名方式。
- 指令句：「先定好命名規則，再統一名稱。」
- 撰寫時遵守：
  - 先確認專案既有的命名規則（Linter 設定、既有程式碼、團隊文件），新程式碼一律遵循；沒有規則時先定下再寫。
  - 依語言慣例：Java 類別 PascalCase、方法與變數 camelCase、常數 UPPER_SNAKE_CASE、套件全小寫；TypeScript 型別與元件 PascalCase、變數與函式 camelCase；資料庫欄位依專案慣例（常見 snake_case）。
  - 同一個概念在整個專案只用一個名稱（不要 user、member、account 混用指同一實體）。
  - 名稱表達用途而非型別或實作（`activeUsers` 而非 `userList2`），布林以 is／has／can 開頭，函式以動詞開頭。
- 違反時的辨識訊號：
  - 同一專案出現 `data`、`user_data`、`UserData` 指同一件事；同一層出現多種大小寫風格。
  - 名稱含無意義的編號或縮寫（`tmp2`、`mgr`、`proc`）。
- 違反時對應手法：27 重新命名變數、28 修改函式宣告。
- 不適用或要小心：與外部系統對接的欄位名稱（第三方 API、既有資料庫 schema）須維持原樣，在邊界做對應轉換，不可為了統一命名而改變對外格式。

## Good Example

- 這個例子是好的，因為同一概念使用單一名稱，且符合語言慣例。

````typescript
interface UserProfile { userId: string; displayName: string; isVerified: boolean; }

function findUserProfile(userId: string): Promise<UserProfile> { /* ... */ }
````

## Bad Example

- 這個例子是壞的，因為同一個概念有三種名稱與兩種大小寫風格。

````typescript
interface user_data { UserID: string; name2: string; verified: boolean; }

function getMember(uid: string): Promise<user_data> { /* ... */ }
const accountInfo = await getMember(id);
````

# Rule 12 - 【100 開放封閉原則】保留既有實作，透過擴充加入功能

- Level: `SHOULD`
- 目的：保留既有實作，透過擴充加入功能。
- 指令句：「依照開放封閉原則，透過擴充來加入新功能。」
- 撰寫時遵守：
  - 在「已確認會反覆新增同類變化」的位置（付款方式、匯出格式、通知管道），設計擴充點：介面＋新實作、註冊表、策略（61）。
  - 新增同類功能時，以新增類別或註冊項目完成，不修改既有、已測試過的實作。
  - 與 82 YAGNI 的取捨：還沒出現第二種變化前不預先抽象；出現第二、第三種時再重構成擴充點。
- 違反時的辨識訊號：
  - 每加一種類型就要在既有類別中再加一個 `case` 或 `else if`，並重新測試整個類別。
  - 修改舊功能的程式碼才能加入新功能，且常因此弄壞舊功能。
- 違反時對應手法：54 多型、61 策略模式、46 工廠函式、60 查找表。
- 不適用或要小心：變化點只有一種且沒有新增跡象時，不建立擴充機制（違反 82 YAGNI、異味 20 過度泛化）。

## Good Example

- 這個例子是好的，因為新增付款方式只要新增一個實作並註冊，既有程式碼不需要修改。

````java
interface PaymentMethod { String code(); void pay(Order order); }

@Component class CreditCardPayment implements PaymentMethod { /* ... */ }
@Component class LinePayPayment implements PaymentMethod { /* 新增的擴充 */ }

class PaymentService {
    private final Map<String, PaymentMethod> methods;
    PaymentService(List<PaymentMethod> all) {
        this.methods = all.stream().collect(toMap(PaymentMethod::code, m -> m));
    }
    void pay(String code, Order order) { methods.get(code).pay(order); }
}
````

## Bad Example

- 這個例子是壞的，因為每新增一種付款方式都要修改這個已測試過的方法。

````java
void pay(String code, Order order) {
    if ("CREDIT".equals(code)) { /* ... */ }
    else if ("ATM".equals(code)) { /* ... */ }
    else if ("LINEPAY".equals(code)) { /* 新增時改這裡 */ }
}
````
