> 檔頭說明：MUST 指每次掃描都必須檢查並回報本異味；是否處理由嚴重度與「不算命中」例外決定，不要求一律修正。量化門檻除 04「超過三層」外皆為補充參考值，專案另有規範時以專案為準。

# Rule 1 - 【01 過長的函式】長到難以閱讀的函式必須拆開

- Level: `MUST`
- 目的：找出長到難以閱讀的函式。
- 指令句：「找出過長的函式，用『抽取函式』把它們拆開。」
- 偵測訊號（任一命中即算）：
  - 函式本體需要捲動才能看完（參考值：超過約 30 行有效程式碼；原圖未給行數門檻，此為掃描參考值，專案另有規範時以專案為準）。
  - 函式內出現用空行或註解分隔的多個「段落」，每段做不同的事（例如「驗證」「計算」「寫檔」）。
  - 需要讀註解才知道某一段在做什麼。
  - 環狀複雜度超過 10 的函式一律視為命中（承接招 88 的量化門檻）。
- 建議搭配手法：26 抽取函式（主要）、37 拆分處理階段、29 抽取變數、41 移動陳述式（先把相關行聚在一起再抽）、55 拆分迴圈。
- 嚴重度建議：中；若同時命中 04 巢狀過深或 11 義大利麵式程式碼，升為高。

## Good Example

- 主函式只剩下幾個有名字的步驟，每一步都能從名稱讀懂用途。

````java
public Receipt checkout(Order order) {
    validate(order);
    Money total = calculateTotal(order);
    Payment payment = charge(order.customer(), total);
    return issueReceipt(order, payment);
}
````

## Bad Example

- 一個函式包辦驗證、計算、扣款、開收據，只能靠註解分段閱讀。

````java
public Receipt checkout(Order order) {
    // 驗證
    if (order.items().isEmpty()) throw new IllegalArgumentException();
    // ...20 行驗證
    // 計算
    BigDecimal total = BigDecimal.ZERO;
    for (Item i : order.items()) { /* ...15 行折扣與稅額 */ }
    // 扣款
    // ...20 行呼叫金流
    // 開收據
    // ...15 行組字串
}
````

# Rule 2 - 【02 重複程式碼】重複邏輯必須集中到一處

- Level: `MUST`
- 目的：集中重複邏輯，避免改一處漏一處。
- 指令句：「找出重複的程式碼，抽成共用函式。」
- 偵測訊號：
  - 兩處以上出現結構相同、只有變數名或常數不同的程式碼片段（約 3 行以上即算）。
  - 同一條業務規則（例如折扣公式、驗證條件）在不同檔案各寫一份。
  - 兄弟子類別中出現內容相同或幾乎相同的方法。
  - 注意：「長得像但代表不同業務知識、未來會各自演變」的程式碼不算命中，需在報告中註明判斷理由。
- 建議搭配手法：26 抽取函式、42 函式參數化（只差數值時）、48 上移方法（重複在兄弟子類別中）、49 抽取父類別、46 工廠函式（重複的是建立物件邏輯）。
- 嚴重度建議：高（三處以上或跨檔案）；中（同檔案兩處）。

## Good Example

- 稅額規則只維護一份，各呼叫端共用。

````java
static BigDecimal withTax(BigDecimal price) {
    return price.multiply(new BigDecimal("1.05")).setScale(0, RoundingMode.HALF_UP);
}
BigDecimal a = withTax(order.price());
BigDecimal b = withTax(refund.price());
````

## Bad Example

- 相同公式複製在兩處，改稅率時必定漏改一處。

````java
BigDecimal a = order.price().multiply(new BigDecimal("1.05")).setScale(0, RoundingMode.HALF_UP);
// ... 另一個檔案
BigDecimal b = refund.price().multiply(new BigDecimal("1.05")).setScale(0, RoundingMode.HALF_UP);
````

# Rule 3 - 【03 命名不清】看不出用途的名稱必須重新命名

- Level: `MUST`
- 目的：讓名稱本身就能說明用途。
- 指令句：「找出看不出用途的名稱，重新命名。」
- 偵測訊號：
  - 單字母或無意義名稱（`x`、`tmp`、`data`、`obj`、`flag`、`val`），迴圈索引 `i`/`j` 與慣用 lambda 參數除外。
  - 名稱與實際內容不符（例如 `list` 實際是 `Map`、`count` 實際是金額）。
  - 函式名稱無法說明做什麼（`process()`、`handle()`、`doIt()`），或名稱只說一半（`save()` 實際上也寄信）。
  - 需要註解解釋變數存什麼。
- 建議搭配手法：27 重新命名變數、28 修改函式宣告、29 抽取變數（為運算式取名）。
- 嚴重度建議：低；若名稱與行為相反、會誤導呼叫端，升為中。

## Good Example

- 名稱直接說明存的是什麼。

````java
BigDecimal totalAmount = unitPrice.multiply(BigDecimal.valueOf(quantity));
````

## Bad Example

- `x` 無法說明用途，讀者必須回推運算才知道是總金額。

````java
BigDecimal x = p.multiply(BigDecimal.valueOf(q));
````

# Rule 4 - 【04 巢狀過深】巢狀超過三層必須攤平

- Level: `MUST`
- 目的：讓多層分支更容易閱讀。
- 指令句：「找出巢狀超過三層的地方，把結構攤平。」
- 偵測訊號：
  - `if` / `for` / `while` / `try` / `switch` / lambda 區塊巢狀超過三層（第四層起即命中）。
  - 縮排呈「階梯狀」，主要邏輯被擠在最深層。
  - 逐層檢查 null 形成的巢狀（`if (a != null) { if (a.b != null) { ... } }`）。
- 建議搭配手法：51 守衛子句（主要）、52 拆解條件式、26 抽取函式（把內層抽出）、65 可選鏈結（逐層 null 檢查）、59 集合處理管線（迴圈內套條件）。
- 嚴重度建議：高。

## Good Example

- 以守衛子句先處理例外情況，主要邏輯不再被擠到深層（行為與下方 Bad Example 相同）。

````java
void ship(Order order) {
    if (order == null) return;
    if (!order.isPaid()) return;
    for (Item item : order.items()) {
        if (!item.inStock()) continue;
        warehouse.ship(item);
    }
}
````

## Bad Example

- 主要邏輯被擠在第四層，呈階梯縮排。

````java
void ship(Order order) {
    if (order != null) {
        if (order.isPaid()) {
            for (Item item : order.items()) {
                if (item.inStock()) {
                    warehouse.ship(item);
                }
            }
        }
    }
}
````

# Rule 5 - 【05 魔術數字】寫死的數字必須改成有名稱的常數

- Level: `MUST`
- 目的：讓寫死的數字有明確含義。
- 指令句：「把魔術數字改成有名稱的常數。」
- 偵測訊號：
  - 程式中出現沒有名稱、需要推算才知道意義的數字或字串字面值（例如 `86400`、`0.05`、`3`、`"A01"`）。
  - 同一個字面值在多處出現。
  - `0`、`1`、`-1`、`""` 在語意自明處（例如索引起點、空字串判斷）不算命中。
- 建議搭配手法：80 DRY 原則（把字面值集中定義為一個具名常數，所有使用處引用它）、67 列舉型別（字面值代表狀態或種類時）、29 抽取變數（字面值只在單一運算式內有意義時）。
- 嚴重度建議：低；若同一數字散落多處且代表業務規則（例如稅率），升為中。

## Good Example

- 常數名稱說明數字含義。

````java
private static final int SECONDS_PER_DAY = 86_400;
long expireAt = now + SECONDS_PER_DAY;
````

## Bad Example

- `86400` 需要讀者自行推算是一天的秒數。

````java
long expireAt = now + 86400;
````

# Rule 6 - 【06 過大的類別】包辦太多職責的類別必須依職責拆開

- Level: `MUST`
- 目的：找出包辦太多職責的類別。
- 指令句：「找出過大的類別，依職責拆開。」
- 偵測訊號：
  - 類別的欄位或方法可分成兩群以上，彼此幾乎不互相使用（例如「設定」「資料」「統計」各一群）。
  - 類別名稱需要用「和」「與」「Manager」「Util」概括。
  - 類別行數明顯過長（參考值：超過約 300 行；原圖未給門檻，此為掃描參考值）。
  - 欄位名稱有共同前綴（例如 `shippingAddress`、`shippingFee`、`shippingDate`），暗示可獨立成類別。
- 建議搭配手法：30 抽取類別（主要）、36 移動函式、38 將函式整合到類別、49 抽取父類別（拆出的是共通行為時）。
- 嚴重度建議：中；若該類別同時命中 10 發散式變更，升為高。

## Good Example

- 設定、資料、統計各自獨立成類別。

````java
class ReportConfig { Locale locale; String format; }
class ReportData   { List<Row> rows; void load(Source s) { /*...*/ } }
class ReportStats  { BigDecimal sum(ReportData d) { /*...*/ } }
````

## Bad Example

- 一個類別同時處理設定、資料載入與統計。

````java
class Report {
    Locale locale; String format;          // 設定
    List<Row> rows; void load(Source s) {} // 資料
    BigDecimal sum() {} BigDecimal avg() {} // 統計
    void exportPdf() {} void sendMail() {} // 輸出
}
````

# Rule 7 - 【07 過長的參數列表】引數太多的函式必須整理參數列表

- Level: `MUST`
- 目的：降低傳錯引數的機率。
- 指令句：「找出引數太多的函式，整理參數列表。」
- 偵測訊號：
  - 參數超過 4 個（參考值；原圖未給門檻）。
  - 連續出現多個相同型別參數（例如三個 `String`、兩個 `LocalDate`），容易傳錯順序。
  - 參數中有布林旗標，用來切換函式行為。
  - 某些參數總是成組出現（同時命中 14 資料群聚）。
- 建議搭配手法：33 引入參數物件、34 移除旗標參數、28 修改函式宣告、30 抽取類別（參數群本身是一個概念時）。
- 嚴重度建議：中；連續相同型別參數超過 3 個時升為高（傳錯順序無法被編譯器抓到）。

## Good Example

- 相關參數包成具名物件，呼叫端不會弄錯順序。

````java
List<Order> find(CustomerId customer, DateRange period, OrderStatus status);
````

## Bad Example

- 多個同型別參數，傳反順序也能編譯通過。

````java
List<Order> find(String customerId, LocalDate from, LocalDate to,
                 String status, boolean includeCanceled, int limit);
````

# Rule 8 - 【08 無用程式碼】沒有任何呼叫端的程式碼必須刪除

- Level: `MUST`
- 目的：移除已經用不到的程式碼。
- 指令句：「找出沒有任何呼叫端的程式碼並刪除。」
- 偵測訊號：
  - 沒有任何呼叫端的函式、類別、欄位、參數。
  - 被註解掉的程式碼區塊。
  - 永遠不會成立的分支（例如 `if (false)`、已移除功能的 feature flag 分支）。
  - 寫入後從未被讀取的變數。
  - 不產生任何效果的陳述式或分支（例如 `x = x + 0`、空的 if 本體）。
- 判斷限制（刪除前必須確認，否則會改壞行為）：
  - 檢查反射、依賴注入、序列化框架、排程設定、XML/YAML 設定、路由表、跨模組或對外公開 API 是否引用。
  - 公開函式庫的 public API 不可直接刪除，須先標記 deprecated。
- 建議搭配手法：82 YAGNI（直接刪除）；若是幾乎沒做事的函式或類別，搭配 31 內聯函式、45 內聯類別。
- 嚴重度建議：低；若無用程式碼會誤導讀者以為仍在使用（例如舊版計價邏輯），升為中。

## Good Example

- 已確認無呼叫端（含反射與設定檔）後才刪除，程式中不留殘骸。

````java
public BigDecimal price(Order o) {
    return pricing.calculate(o);
}
````

## Bad Example

- 保留註解掉的舊程式碼與沒有呼叫端的舊方法。

````java
public BigDecimal price(Order o) {
    // return oldPricing.calc(o) * 1.1;
    return pricing.calculate(o);
}
private BigDecimal legacyPrice(Order o) { /* 無呼叫端 */ }
````

# Rule 9 - 【09 散彈式修改】找出只改一件事卻得動到好幾個檔案的地方

- Level: `MUST`
- 目的：避免一個改動散落在多個檔案。
- 指令句：「找出只改一件事、卻得動到好幾個檔案的地方。」
- 偵測訊號：
  - 新增一個欄位、一種狀態或一條規則時，需要同步修改三個以上檔案（參考 git log：同一主題的 commit 每次都修改同一組檔案）。
  - 同一個概念的邏輯（例如「會員等級折扣」）散布在 controller、service、util 多處。
  - 與 02 重複程式碼、16 重複的 switch 常一起出現。
- 建議搭配手法：36 移動函式、38 將函式整合到類別、45 內聯類別（把散落的小類別併回）、30 抽取類別（集中成新的職責單位）。
- 嚴重度建議：高。

## Good Example

- 會員等級相關規則集中在同一類別，新增等級只改一處。

````java
enum MemberLevel {
    GOLD(new BigDecimal("0.9")), SILVER(new BigDecimal("0.95"));
    final BigDecimal discount;
    MemberLevel(BigDecimal d) { discount = d; }
}
````

## Bad Example

- 新增一個會員等級要同時改三個檔案。

````java
// OrderService.java
if (level.equals("GOLD")) rate = 0.9;
// InvoiceUtil.java
if (level.equals("GOLD")) label = "金卡";
// ReportController.java
if (level.equals("GOLD")) color = "gold";
````

# Rule 10 - 【10 發散式變更】因不同需求而修改的元件必須依職責拆開

- Level: `MUST`
- 目的：拆開因不同原因而修改的部分。
- 指令句：「找出常因不同需求而修改的元件，依職責拆開。」
- 偵測訊號：
  - 同一個類別或檔案會因為兩種以上互不相關的原因被修改（例如「換資料庫」與「改計價規則」都要動它）。
  - 類別中的方法可分組，每組只和某一種外部變動有關。
  - 與 09 方向相反：09 是「一個原因改多處」，10 是「一處因多個原因被改」。
- 建議搭配手法：30 抽取類別（主要）、37 拆分處理階段、36 移動函式。
- 嚴重度建議：高。

## Good Example

- 資料存取與計價規則分屬不同類別，各自只因一種原因改變。

````java
class OrderRepository { Order findById(long id) { /* SQL */ } }
class PriceCalculator  { BigDecimal price(Order o) { /* 規則 */ } }
````

## Bad Example

- 換資料庫或改計價規則都得改同一個類別。

````java
class OrderService {
    Order findById(long id) { /* JDBC SQL */ }
    BigDecimal price(Order o) { /* 折扣、稅額規則 */ }
}
````

# Rule 11 - 【11 義大利麵式程式碼】交錯糾結的流程必須理順

- Level: `MUST`
- 目的：理順交錯的執行流程。
- 指令句：「整理糾結的流程，讓執行順序可以一路追蹤。」
- 偵測訊號：
  - 執行順序無法由上往下一路追蹤：大量跳躍（`goto`、多處 `continue`/`break` 搭配旗標）、回呼互相交錯。
  - 同一變數在流程中多處被改寫，讀者必須來回對照才知道當下值。
  - 相關陳述式分散，彼此之間穿插不相干的邏輯。
  - 以多個布林旗標控制流程走向。
- 建議搭配手法：41 移動陳述式（先讓相關程式碼相鄰）、37 拆分處理階段、26 抽取函式、51 守衛子句、58 移除控制旗標、73 狀態機（多旗標組合時）、40 替換演算法。
- 嚴重度建議：高。

## Good Example

- 流程分成清楚的階段，由上往下即可追蹤。

````java
List<Row> rows = read(file);
List<Row> valid = rows.stream().filter(Row::isValid).toList();
write(summarize(valid));
````

## Bad Example

- 旗標與交錯的讀寫讓執行順序難以追蹤。

````java
boolean ok = false; int n = 0;
for (String line : lines) {
    if (!ok) { if (line.startsWith("#")) { ok = true; continue; } }
    n++;
    if (ok && n > 3) { out.write(line); ok = false; }
    else if (!ok) { buffer.add(line); }
}
````

# Rule 12 - 【12 全域變數】全域變數必須改成透過引數傳入

- Level: `MUST`
- 目的：避免變數從各處被任意改寫。
- 指令句：「找出全域變數，改成透過引數傳入。」
- 偵測訊號：
  - 可寫的 `static` 欄位、全域物件、單例中的可變狀態，被多個類別或函式直接讀寫。
  - 函式結果依賴未出現在參數列中的外部可變狀態。
  - 不可變的常數（`static final` 且內容不可變）不算命中。
- 建議搭配手法：28 修改函式宣告（加入參數，改由引數傳入）、47 封裝變數（暫時無法消除時，至少收斂讀寫入口）、93 相依性注入（見 `rules/設計原則.md`，供參考）。
- 嚴重度建議：高（多執行緒或多處寫入）；中（只有單處寫入、多處讀取）；中（public 可寫但本次審查範圍內未見寫入點，報告中須註明「需查外部呼叫端是否寫入」）。

## Good Example

- 所需資料由引數傳入，函式結果只取決於輸入。

````java
BigDecimal price(Order order, BigDecimal taxRate) {
    return order.subtotal().multiply(BigDecimal.ONE.add(taxRate));
}
````

## Bad Example

- 依賴可被任意改寫的全域變數。

````java
public static BigDecimal TAX_RATE = new BigDecimal("0.05"); // 任何地方都能改
BigDecimal price(Order order) {
    return order.subtotal().multiply(BigDecimal.ONE.add(Globals.TAX_RATE));
}
````

# Rule 13 - 【13 特性依戀】大量使用其他類別資料的函式必須移到該類別

- Level: `MUST`
- 目的：讓操作靠近它主要使用的資料。
- 指令句：「把大量使用其他類別資料的函式移到該類別。」
- 偵測訊號：
  - 函式呼叫另一個物件的 getter 次數明顯多於使用自身欄位（參考值：對同一外部物件取值 3 次以上，且幾乎不用 `this` 的成員）。
  - 函式內反覆出現 `other.getX()`、`other.getY()` 組合計算。
- 建議搭配手法：36 移動函式（主要）、26 抽取函式（只有部分片段依戀時，先抽出再移動）。
- 嚴重度建議：中。

## Good Example

- 計算放在擁有資料的類別裡。

````java
class Order {
    BigDecimal shippingFee() {
        return weight.compareTo(LIMIT) > 0 ? HEAVY_FEE : NORMAL_FEE;
    }
}
````

## Bad Example

- `Calculator` 只在操作 `Order` 的資料。

````java
class Calculator {
    BigDecimal shippingFee(Order o) {
        return o.getWeight().compareTo(o.getLimit()) > 0 ? o.getHeavyFee() : o.getNormalFee();
    }
}
````

# Rule 14 - 【14 資料群聚】總是一起出現的值必須封裝成一組

- Level: `MUST`
- 目的：把總是一起出現的值放在一起。
- 指令句：「將經常一起傳遞的值封裝成一組。」
- 偵測訊號：
  - 兩到三個以上的值在多個函式參數列、欄位組合中總是一起出現（例如 `startDate, endDate`、`city, zip, street`）。
  - 判斷法：刪掉其中一個值後，其他值就失去意義，即為群聚。
- 建議搭配手法：33 引入參數物件、30 抽取類別。
- 嚴重度建議：中。

## Good Example

- 地址相關的值封裝成一個型別。

````java
record Address(String city, String zip, String street) {}
void ship(Order order, Address to);
````

## Bad Example

- 三個值在多個函式中一起傳遞。

````java
void ship(Order order, String city, String zip, String street);
void bill(Invoice inv, String city, String zip, String street);
````

# Rule 15 - 【15 過度依賴基本型別】領域概念必須用專用型別表達

- Level: `MUST`
- 目的：用專用型別表達領域概念。
- 指令句：「把電話號碼這類值封裝成專用型別。」
- 偵測訊號：
  - 電話、Email、金額、幣別、ID、單位等領域概念以 `String`、`int`、`double` 表示。
  - 同一格式驗證（例如電話格式檢查）在多處重複。
  - 用字串或整數代表狀態或種類（例如 `"open"`、`1 = 已付款`）。
  - 用 `double` 表示金額。
- 建議搭配手法：30 抽取類別（建立值物件）、67 列舉型別（狀態或種類）、46 工廠函式（集中驗證與建立）。
- 嚴重度建議：中；金額用浮點數、或格式驗證散落多處時升為高。

## Good Example

- 電話號碼有自己的型別，驗證集中在建構時（範例中的格式僅為示意，實際格式依專案需求）。

````java
record PhoneNumber(String value) {
    // 示意用的寬鬆格式：090-1234-5678、0912-345-678、02-2345-6789 皆可；格式依實際需求調整
    private static final Pattern FORMAT = Pattern.compile("\\d{2,4}-\\d{3,4}-\\d{3,4}");
    PhoneNumber {
        if (!FORMAT.matcher(value).matches()) throw new IllegalArgumentException(value);
    }
}
void notify(PhoneNumber phone);
````

## Bad Example

- 以字串表示電話，任何字串都能傳入。

````java
void notify(String phone); // "090-1234-5678"、"abc" 都能傳
````

# Rule 16 - 【16 重複的 switch】找出多個地方重複出現的 switch 敘述

- Level: `MUST`
- 目的：找出散落各處的相同分支。
- 指令句：「找出多個地方重複出現的 switch 敘述。」
- 偵測訊號：
  - 兩處以上對同一個型別碼、列舉或字串做 `switch` 或 `if/else if` 鏈，分支項目相同。
  - 新增一個種類時，需要逐一找出所有 switch 補上分支（同時命中 09 散彈式修改）。
- 建議搭配手法：54 多型（主要）、61 策略模式、60 查找表（分支只對應資料時）、69 模式比對、46 工廠函式（把唯一保留的 switch 集中在建立處）。
- 嚴重度建議：高（三處以上）；中（兩處）。

## Good Example

- 各型別各自實作行為，不必在各處 switch。

````java
sealed interface Shape permits Circle, Square {
    double area();
    String label();
}
````

## Bad Example

- 相同的 switch 在多處出現。

````java
double area(Shape s)   { switch (s.type()) { case CIRCLE: ...; case SQUARE: ...; } }
String label(Shape s)  { switch (s.type()) { case CIRCLE: ...; case SQUARE: ...; } }
````

# Rule 17 - 【17 暫時欄位】找出只在特定情況下才有值的欄位

- Level: `MUST`
- 目的：找出偶爾才會用到的欄位。
- 指令句：「找出只在特定情況下才有值的欄位。」
- 偵測訊號：
  - 欄位只在某個方法執行期間或特定狀態下才被賦值，其他時候為 `null` 或預設值。
  - 欄位被用來在方法之間傳遞暫存值，而不是表達物件狀態。
  - 讀取該欄位前總要先檢查是否為 null。
- 建議搭配手法：30 抽取類別（把暫時欄位與使用它的方法搬到新類別）、56 引入特殊案例（欄位缺值時的處理集中）、28 修改函式宣告（改用參數或區域變數傳遞）。
- 嚴重度建議：中。

## Good Example

- 暫存值改為區域變數，只活在需要它的範圍。

````java
Route plan(Order order) {
    List<Stop> stops = collectStops(order);
    return optimize(stops);
}
````

## Bad Example

- `tempStops` 只在 `plan()` 執行期間有值，其他時候為 null。

````java
class Planner {
    private List<Stop> tempStops; // 平常為 null
    Route plan(Order order) { tempStops = collectStops(order); return optimize(); }
    private Route optimize() { /* 讀 tempStops */ }
}
````

# Rule 18 - 【18 呼叫鏈過長】一層接一層的長呼叫鏈必須縮短

- Level: `MUST`
- 目的：縮短一層接一層的呼叫。
- 指令句：「縮短像 a.b().c().d() 這樣的長呼叫鏈。」
- 偵測訊號：
  - 透過取得物件再取得物件的方式存取深層資料，連續三層以上（例如 `order.getCustomer().getAddress().getCity()`）。
  - 呼叫端因此得知並依賴中間物件的內部結構。
  - 不算命中：Fluent API / Builder / Stream 管線（每一步回傳同一抽象或設計上就是鏈式呼叫）。
- 建議搭配手法：43 隱藏委派（主要）、26 抽取函式後 36 移動函式（把鏈尾使用邏輯移到鏈中適當物件）、92 迪米特法則（見 `rules/設計原則.md`，供參考）。
- 嚴重度建議：中。

## Good Example

- 呼叫端只和直接認識的物件互動。

````java
String city = order.shippingCity();
````

## Bad Example

- 呼叫端必須知道 Order → Customer → Address 的內部結構。

````java
String city = order.getCustomer().getAddress().getCity();
````

# Rule 19 - 【19 中間人】找出把工作原封不動轉交出去的類別

- Level: `MUST`
- 目的：找出只負責轉呼叫的類別。
- 指令句：「找出把工作原封不動轉交出去的類別。」
- 偵測訊號：
  - 類別中多數方法（參考值：一半以上）只是把呼叫原封不動轉給另一個物件，沒有加入任何邏輯。
  - 呼叫端經由 A → 中間 → B，但中間層不提供封裝、轉換、權限或交易等額外價值。
  - 不算命中：刻意設計的防腐層、Facade、Adapter、Proxy（有明確隔離目的時須在報告註明）。
- 建議搭配手法：44 移除中間人（主要）、31 內聯函式、45 內聯類別。
- 嚴重度建議：低。

## Good Example

- 呼叫端直接使用真正做事的物件。

````java
Department dept = person.department();
Person manager = dept.manager();
````

## Bad Example

- `Person` 的方法只是把呼叫轉給 `Department`。

````java
class Person {
    Person manager()      { return department.manager(); }
    String deptName()     { return department.name(); }
    List<Person> peers()  { return department.members(); }
}
````

# Rule 20 - 【20 過度泛化】找出目前用不到、先為擴充而做的機制

- Level: `MUST`
- 目的：清掉為未來預留的擴充機制。
- 指令句：「找出目前用不到、先為擴充而做的機制。」
- 偵測訊號：
  - 只有一個實作的介面或抽象類別，且沒有測試替身等實際需求。
  - 從未被傳入不同值的參數、從未被覆寫的 hook 方法、只有一個選項的設定開關。
  - 命名含 `Abstract`、`Base`、`Generic`、`Plugin`，但實際只有一種用法。
- 建議搭配手法：50 攤平類別階層、45 內聯類別、31 內聯函式、28 修改函式宣告（移除沒用到的參數）；原則上對應 82 YAGNI。
- 嚴重度建議：低；若泛化層使閱讀路徑大幅變長，升為中。

## Good Example

- 目前只有一種通知方式，就直接寫具體類別。

````java
class EmailNotifier {
    void send(String to, String body) { mail.send(to, body); }
}
````

## Bad Example

- 為未來可能的通知管道預留抽象層，但只有一個實作。

````java
interface Notifier<T extends Message, C extends Channel> { void send(T m, C c); }
abstract class AbstractNotifier<T extends Message, C extends Channel> implements Notifier<T, C> {}
class EmailNotifier extends AbstractNotifier<EmailMessage, EmailChannel> { /* 唯一實作 */ }
````

# Rule 21 - 【21 閒置類別】幾乎沒有職責的類別必須合併

- Level: `MUST`
- 目的：合併幾乎沒有職責的類別。
- 指令句：「找出幾乎沒做事的類別，將它合併。」
- 偵測訊號：
  - 類別只有一兩個簡單方法或欄位，且只被一個地方使用。
  - 重構後職責被搬走、只剩空殼的類別。
  - 存在的理由只是「以後可能會長大」。
- 建議搭配手法：45 內聯類別（主要）、50 攤平類別階層（閒置的是父類別或子類別時）。
- 嚴重度建議：低。

## Good Example

- 幾乎沒做事、又不代表獨立領域概念的類別併回唯一使用端。

````java
class Shipment {
    private String trackingCompany;
    private String trackingNumber;
    String trackingInfo() { return trackingCompany + ": " + trackingNumber; }
}
````

## Bad Example

- `TrackingInformation` 幾乎沒做事，只被 `Shipment` 使用。

````java
class TrackingInformation { String company; String number; }
class Shipment {
    TrackingInformation tracking;
    String trackingInfo() { return tracking.company + ": " + tracking.number; }
}
````

# Rule 22 - 【22 資料類別】只存資料的類別必須把相關操作移進來

- Level: `MUST`
- 目的：讓資料與相關行為放在一起。
- 指令句：「把相關操作移進只存放資料的類別。」
- 偵測訊號：
  - 類別只有欄位與 getter/setter，對這些資料的計算、驗證都寫在其他類別。
  - 外部類別經常取出它的欄位做相同的計算（同時命中 13 特性依戀）。
  - 欄位有公開 setter，外部可任意改寫。
  - 不算命中：純 DTO、API 回應物件、資料庫映射層等刻意只承載資料的邊界物件。
- 建議搭配手法：36 移動函式（主要）、47 封裝變數（收斂 setter）、38 將函式整合到類別。
- 嚴重度建議：中。

## Good Example

- 與資料相關的計算放在類別內。

````java
class Rectangle {
    private final double width, height;
    double area() { return width * height; }
}
````

## Bad Example

- 只有 getter/setter，計算寫在外部。

````java
class Rectangle { double width, height; /* getter/setter */ }
class Geometry { double area(Rectangle r) { return r.getWidth() * r.getHeight(); } }
````

# Rule 23 - 【23 平行繼承階層】找出一邊新增子類別、另一邊也得跟著加的繼承結構

- Level: `MUST`
- 目的：找出必須成對擴充的繼承階層。
- 指令句：「找出一邊新增子類別，另一邊也得跟著加的繼承結構。」
- 偵測訊號：
  - 兩棵繼承樹的子類別一一對應，且命名有共同前綴（例如 `PdfReport` / `PdfExporter`、`CsvReport` / `CsvExporter`）。
  - 新增一個子類別時，一定得到另一棵樹也新增對應子類別。
- 建議搭配手法：36 移動函式（把一棵樹的行為移入另一棵，使其中一棵消失）、50 攤平類別階層、48 上移方法；若對應關係無法消除，改由 61 策略模式組合。
- 嚴重度建議：中。

## Good Example

- 匯出行為合併到報表本身，只剩一棵繼承樹。

````java
abstract class Report { abstract byte[] export(); }
class PdfReport extends Report { byte[] export() { /* PDF */ } }
class CsvReport extends Report { byte[] export() { /* CSV */ } }
````

## Bad Example

- 每加一種報表，就得同時加一個匯出器。

````java
abstract class Report {}       class PdfReport extends Report {}   class CsvReport extends Report {}
abstract class Exporter {}     class PdfExporter extends Exporter {} class CsvExporter extends Exporter {}
````

# Rule 24 - 【24 拒絕繼承】找出幾乎沒用到父類別功能的子類別

- Level: `MUST`
- 目的：找出子類別用不到的繼承功能。
- 指令句：「找出幾乎沒用到父類別功能的子類別。」
- 偵測訊號：
  - 子類別只使用父類別少數方法，其餘方法被覆寫成空實作或丟出 `UnsupportedOperationException`。
  - 子類別與父類別不是真正的「是一種」關係，只是為了重用部分程式碼而繼承。
- 建議搭配手法：50 攤平類別階層（父子差異不大時）、30 抽取類別（把子類別真正需要的部分抽出，改用組合持有）、36 移動函式（把只有部分子類別需要的方法從父類別移到需要它的子類別）。
- 嚴重度建議：中；子類別以丟例外拒絕父類別方法時升為高（呼叫端依父型別使用時會在執行期失敗）。

## Good Example

- 不是「是一種」的關係就改用組合，只暴露需要的功能。

````java
class Stack<T> {
    private final List<T> items = new ArrayList<>();
    void push(T t) { items.add(t); }
    T pop() { return items.remove(items.size() - 1); }
}
````

## Bad Example

- 為了重用而繼承，再用例外拒絕用不到的父類別方法。

````java
class Stack<T> extends ArrayList<T> {
    @Override public T get(int i) { throw new UnsupportedOperationException(); }
    @Override public void add(int i, T t) { throw new UnsupportedOperationException(); }
}
````

# Rule 25 - 【25 類別過度耦合】互相存取內部細節的類別必須降低耦合

- Level: `MUST`
- 目的：拆開彼此存取內部細節的類別。
- 指令句：「找出互相操作內部資料的類別，降低耦合。」
- 偵測訊號：
  - 兩個類別雙向相依，且彼此直接讀寫對方的欄位或內部集合（例如 `a.getItems().add(...)`）。
  - 為了讓另一個類別存取而把欄位改成 package-private / public，或回傳可變的內部集合。
  - 修改其中一個類別的內部結構，另一個類別必定跟著壞。
- 建議搭配手法：36 移動函式、47 封裝變數（不回傳可變內部資料）、43 隱藏委派、30 抽取類別（把雙方共用的部分抽成第三個類別）。
- 嚴重度建議：高。

## Good Example

- 透過對外方法操作，不直接改對方內部集合。

````java
class Order {
    private final List<Item> items = new ArrayList<>();
    void addItem(Item item) { items.add(item); recalculate(); }
    List<Item> items() { return List.copyOf(items); }
}
````

## Bad Example

- 外部類別直接修改 `Order` 的內部集合，`Order` 也直接改 `Cart` 的欄位。

````java
cart.getOrder().getItems().add(item);
cart.getOrder().total = cart.getOrder().total.add(item.price());
// Order 內部
this.cart.lastModified = now;
````

# Rule 26 - 【補充·對應手法 71】吞掉例外

- Level: `MUST`
- 目的：找出把例外吃掉、讓錯誤無聲消失的程式碼。
- 補充說明：找出吞掉例外的地方，標記為異味（本條非原圖內容；修正做法見 `rules/條件分支與迴圈整理手法.md` 的 71 吞掉例外，本條不重複）。
- 性質：本條是原 01–25 異味清單之外的補充異味；審查報告中「異味編號」欄填 `71`（沿用對應手法的編號）。
- 偵測訊號：
  - 空的 catch 區塊，或 catch 內只有註解（例如 `// ignore`）。
  - catch 內只印 stack trace（`e.printStackTrace()`、`console.log(e)`），未進入正式日誌系統，也沒有後續處理。
  - catch 後回傳預設值（`null`、`0`、空集合、`false`）卻沒有任何日誌。
  - 重新拋出新例外時沒有帶上原例外（cause 遺失）。
  - Promise 使用 `.catch(() => {})`，或 async 回傳的 Promise 未被 await 也未處理錯誤。
- 判斷限制：catch 內已以註解寫明忽略理由且有 debug／warn 等級日誌者，不算命中。
- 建議搭配手法：71 吞掉例外（主要）、62 快速失敗。
- 嚴重度建議：高。

## Good Example

- 例外沒有被吞掉：留有日誌，且帶著 cause 往上拋。

````java
try {
    return gateway.charge(order);
} catch (GatewayException e) {
    log.error("charge failed, orderId={}", order.id(), e);
    throw new PaymentFailedException(order.id(), e);
}
````

## Bad Example

- 空 catch 加上回傳預設值，錯誤無聲消失，呼叫端以為只是沒資料。

````java
try {
    return gateway.charge(order);
} catch (Exception e) {
    return null;
}
````
